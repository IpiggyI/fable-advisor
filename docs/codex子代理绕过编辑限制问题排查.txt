● 调查结论

  根因：上次的"硬限制"没有失效——它根本没有被加载。修复的两道防线都是 prompt
  文本，而这次事故会话中，两段文本一段没进 orchestrator
  的上下文，另一段（按上次已证明的机制）永远进不了被误派的子代理的上下文。

  事故复现链（全部来自磁盘取证）

  1. spawn 又传了 name。主会话的 Agent 调用参数：subagent_type=fable-advisor:cod
  ex-implementer，name=codex-facts。子代理 meta.json 实锤：taskKind: 
  "in_process_teammate"、permissionMode: 
  "bypassPermissions"——和上次事故（dd6c4dbd）完全同型：传 name → teammate 通道 →
  工具白名单被抹掉。
  2. 子代理拿到了全套工具并自己干了活：26 次 Bash、17 次 Edit、0 次 codex exec
  真实执行（transcript 里 "codex exec" 出现 15 次全是 spec/消息文本；唯一含
  "codex" 的 Bash 只是检查 ~/.codex/docs 的 junction）。主会话后来 SendMessage
  质询它是否真调了 codex——你看到的正是这个环节。

  两道防线为什么都没起作用

  防线一（orchestration SKILL.md 的 "never pass name" doctrine）——没被加载。
  这段 doctrine 在这台机器的 cache 3.1.0 里确实存在（部署没问题），但它住在
  skill 文件里，只有 orchestration skill 
  被实际调用时才进上下文。本次主会话从头到尾只调用了 /effort 和
  /trellis:continue；grep 整个主会话 jsonl，"Spawning the CLI lanes" 和 "never
  pass" 出现次数都是 0。orchestrator 能看到的只有系统提示里 agent 列表的
  description——而 codex-implementer 的 description
  里没写"必须无名派生"。于是它按直觉给子代理起了个名字。

  防线二（codex-implementer.md 的 "Spawn contract" 自检）——存在逻辑死角。
  上次调查已经证明：teammate 通道不注入 agent 定义的系统提示词。本次子代理
  transcript 里 "Spawn contract"、"never implement the task yourself"、"command
  -v codex" 计数全部为 0——定义又没进上下文。也就是说，这条"发现自己有 Write/Edit
  就自报误派"的自检，恰好只在它唯一需要生效的场景（被误派为 
  teammate）下收不到；在能收到它的 local_agent
  通道里，护栏本来就没破。这道防线设计上就永远不会触发。

  回答你的核心问题

  "明明加了硬限制，子代理如何继续获得编辑权限？"——因为上次的修复不是机制层的硬限
  制，而是行为约定：真正的机制缺陷（teammate 通道忽略 tools 白名单）在 Claude
  Code harness 内部，插件改不了；修复只能约定"orchestrator 别传
  name"。而这个约定的唯一可靠载体（orchestration
  skill）不会自动加载——在一个没触发该 skill 的普通会话（本次是 trellis
  工作流）里，doctrine 等于不存在，一切回到修复前。
