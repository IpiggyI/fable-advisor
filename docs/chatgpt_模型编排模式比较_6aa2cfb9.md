# 模型编排模式比较
*创建时间: 09/10/2026, 11:41 PM*

## 1. User

思考一个问题：
纯粹使用高档模型（astra、fable）进行完整的开发工作成本非常地高，现在有很多人都在研究如何将其和廉价模型搭配起来干活，常见的处理方式是用“编排器模式”来平衡性能和成本，
主要有三类实现方式：
1. 高级模型编排、轻量模型实现。例如在主代理中使用GPT-6-Astra进行规划再委派给GPT-5.6-Luna子代理进行实现
2. 轻量模型编排、高级模型实现。例如在主代理中使用GPT-5.6-Luna进行编排再委派给GPT-6-Astra子代理进行实现
3. 轻量模型实现、高级模型评审。在主代理中使用轻量模型进行实现，在需要时询问高级模型的建议，目前Claude Code的advisor应该就是这一个模式。例如和GPT-5-Luna进行沟通实现，操作前询问GPT-6-Astra的意见
你认为这几种模式哪一个更好一些（成本、性能、或者两个角度都是）？目前各大社区中对这两种做法的一个评价怎么样？
然后就我个人的使用感受以及观察到其他人的看法大致如下：
首先，高+低的组合最不适用；此时高级模型依然会有大量的工作，还需要和子代理不断地沟通，需要检查子代理的结果，必要时还需要安排返工（若干轮次），可能还不如全称自己干来的快/准确/便宜
低+高（编排版）通常更好，但有个前提是开发计划已经提前备好（可以是提前跟高级模型沟通后订好一版计划）然后让轻量模型对着计划进行派工，这样子高级模型就只需要领取一块独立的、明确的任务，而且高级模型去做的话返工次数肯定会比轻量模型少很多，并且检查结果这种活通常并不需要很高的智能，轻量模型可能无法解决某个难题但验证问题是否被解决应该还是能做得到的
低+高（评审版）我认为就是实现最终还是由轻量模型来完成的，而高级模型评审也是会去读取大量上下文的，所以他的效果应该是介于前两者之间；但它最大的问题是轻量模型它不一定或者说不知道什么时候要去问高级模型（或者强制它在实现前让高级模型把把关？但这样频率又是一个问题）

## 4. AI

**就你描述的使用方式——先把开发计划讨论清楚，再让代理完成实现，重视交付质量，也不希望自己频繁救火——我更倾向于第二种：轻量模型调度，强模型完成有明确边界的任务。**

但我会修正你判断里的两个部分：

**第一，“高编排＋低实现最不适用”不能普遍成立。** 它确实容易变成昂贵模型带着廉价模型反复返工，但也存在明显适合它的任务结构。

**第二，“低实现＋高评审的效果介于两者之间”也不一定。** 它既可能比强模型单干更划算，也可能在准确率上超过强模型单干，只是更贵；决定因素不是组织形式本身，而是问题究竟卡在“想不到办法”，还是“知道办法也做不对”。

下面把**我的判断、产品的实际机制、社区经验和有测量数据的实验**分开说。产品信息以 **2026 年 9 月 10 日**查到的资料为准。

## 一、三种模式真正的区别：谁在承担反复发生的工作

我认为，与其看谁是“主代理”，不如看三件事：

**谁在作重要决定，谁在执行高频循环，谁在为错误买单。**

| 模式 | 理想状态 | 最容易出现的问题 |
|---|---|---|
| ① 强编排＋轻量实现 | 强模型消除歧义，轻量模型批量完成明确任务 | 强模型不断读结果、解释、验收、重新派工，实际上一直没有退出 |
| ② 轻量编排＋强实现 | 轻量模型管理流程，强模型独立完成实质任务 | 轻量模型错误拆分任务、遗漏依赖，或没有发现强模型产出的全局问题 |
| ③ 轻量实现＋强顾问 | 轻量模型能执行，只在少数关键判断上需要帮助 | 不知道何时求助；或者顾问知道怎么办，执行模型仍然做不到 |

这张表是我的分析框架，不是已经得到统一实验验证的排名。

尤其需要区分：**“编排”到底是智能决策，还是流程调度？**

如果只是按已经确定的任务列表启动代理、等待结果、运行检查、记录状态，那么它更接近调度器，部分工作甚至可以直接用程序完成。

但如果还包括“发现计划不对、重新划分模块、判断两个方案哪个合理、解决跨模块冲突”，那就仍然是高认知负荷的开发工作。把它放在廉价模型上，并不会因为它叫“编排”就变得简单。

## 二、关于第一种：你指出的失败机制非常准确，但它有适用区间

你描述的情况可以概括为：

> 强模型没有真正把工作交出去，只是把直接写代码，换成了指导另一个模型写代码。

原本一个强模型能完成的“理解问题—修改—测试”循环，变成：

**解释任务 → 廉价模型尝试 → 强模型理解尝试结果 → 发现问题 → 重新解释 → 再次尝试。**

这里新增的并不只是几句沟通，而是每一轮都可能重新发生的理解、判断和上下文传递。因此，**“工人模型很便宜”不等于“整件事便宜”。**

### 什么情况下，你的判断最容易成立？

我的判断是：当任务具有以下组合时，第一种尤其不划算——**实现本身不容易、子任务相互依赖、验收难以自动化，而且强模型必须频繁介入细节。**

例如修复一个跨缓存、数据库事务和并发控制的问题。把它拆给几个廉价代理，并不一定降低认知难度，反而可能增加“各自局部正确、组合起来错误”的机会。

### 什么情况下，第一种反而合适？

关键是：**强模型一次决策，能够替代多少后续强模型工作？**

假设强模型确定了迁移规则、接口契约和验收方式，随后有大量相似、相对独立的修改需要执行，而这些修改能用既定测试或静态检查验证，那么强模型的规划成本就有机会被摊薄。

所以我不会把第一种概括为“强模型当老板，廉价模型当员工”，而会要求它满足：

> **强模型负责少量不可替代的判断，廉价模型承担大量能自行完成的工作。**

如果廉价模型每走几步就需要强模型重新解释，那不是成功的分工，而是失败的能力匹配。

这也解释了为什么一些真实工程实验能支持第一种，另一些个人开发实验却得出相反结论，后面会给具体例子。

## 三、关于第二种：我最认同你的方向，但“验证容易”需要加一个很重要的限定

### 1. 你提出的其实是“强规划—轻调度—强执行”

你已经补充了最重要的前提：

> 开发计划提前准备好，可以先跟高级模型讨论。

这意味着，轻量模型并不是承担了全部编排智能，而是**接手了已经被强模型降低难度的调度工作**。

我认为这是一种合理的设计，而不是作弊。但比较成本时，需要把前期规划计入；如果计划可以服务后续很多任务，才应当把它摊销，而不是直接当作免费。

另外，计划不能只是一串待办事项。为了让轻量调度器真正不需要作太多判断，计划最好同时规定：任务边界、依赖顺序、接口约束、验收依据，以及什么情况必须返回重新规划。

**没有“什么时候计划失效”的规则，轻量调度器可能非常认真地执行一个已经不适用的计划。**

### 2. “不会解决，但会验证”有两种完全不同的含义

你这个判断**对一部分验证成立，但不能扩大到全部软件验收**：

| 验证内容 | 是否适合轻量模型或程序 |
|---|---|
| 编译是否通过、指定测试是否通过、输出是否符合既定格式 | 很适合，很多根本不需要模型判断 |
| 是否满足既定验收清单、是否改动了不允许修改的文件 | 可以交给轻量模型辅助，但应保留客观证据 |
| 测试是否充分、需求是否被误解、是否引入隐藏的跨模块问题 | 不能默认比实现简单，需要更强判断或人工参与 |

举一个假设例子：模型修好了某个接口，现有测试全部通过，但测试没有覆盖“用户能否读取其他用户的数据”。

此时轻量模型完全可能正确地确认“测试通过”，却错误地推出“任务完成”。问题不在于它不会运行测试，而在于**验收条件本身没有覆盖真正的正确性**。

因此，我会把你的判断改写成：

> **轻量模型可以核对强模型提交的验收证据，但不应独自定义何为合格，也不应成为所有高风险变更的最终裁判。**

### 3. 第二种更有希望提高交付稳定性，但未必最省 API 费

既然实现主要交给强模型，那么代码探索、修改、调试等实质工作，仍然按强模型价格计费。

它节省的是调度开销，以及可能通过清晰任务边界减少的重复探索和返工；**不是把主要实现成本都变便宜了。**

所以，针对你的目标，我会优先测试第二种；但如果目标改成“尽可能压低账单”，而多数实现任务廉价模型已经能做好，那么第三种或第一种可能更便宜。

你说“强模型返工肯定少很多”，我也会稍微收紧：这是值得期待和实测的优势，不应当作为保证。错误的任务描述、遗漏的依赖和不完整的上下文，同样会让强模型走错方向。

## 四、关于第三种：关键不是“评审够不够聪明”，而是建议能不能转化成正确实现

这里需要先校正一下对 Claude Code advisor 的理解。

当前 advisor 会接收完整对话，包括已有工具调用及结果；但 **advisor 本身不能调用工具**，不能自行继续查仓库、运行测试或修改代码。它返回建议，后续仍由执行模型完成。因此，它更准确地说是“基于执行轨迹提供建议的顾问”，并不等同于一个拥有独立工具权限的强模型评审代理。([Claude](https://code.claude.com/docs/en/advisor))

这会产生两类完全不同的情况。

### 情况 A：轻量模型缺的是正确方向

例如它一直修改错误的位置，强顾问看了已有证据，指出应该检查配置加载顺序。剩下的修改和验证都不难。

这时第三种可能非常有效：**强模型用少量判断，终止了廉价模型的大量无效尝试。**

### 情况 B：轻量模型缺的是实现能力

例如强顾问已经指出应该怎样处理复杂并发关系，但执行模型仍反复写错状态转换。

这时继续增加顾问调用，不一定解决问题。顾问可能不得不把建议写得越来越接近完整补丁，再由轻量模型转述和应用。

**到了这个阶段，应当让强模型接管实现，而不是继续维持“廉价模型主导”的形式。**

所以我更喜欢：

> **轻量实现 → 必要时咨询 → 咨询后仍不能收敛，就升级为强模型执行。**

而不是无限循环的“轻量实现—强模型指出错误—轻量再改”。

### 你担心“它不知道什么时候问”，这个问题确实存在

Anthropic 的 API 文档明确写到：缺少系统提示引导时，执行模型在部分领域会调用顾问不足，尤其是编码任务。官方建议的两个重要时点，是**做过初步探索后、开始实质工作前**，以及困难任务中**修改和测试完成后、宣布完成前**。([Claude Platform](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool))

但要注意，**Claude Code 当前没有用于强制调用或限制调用次数的专门设置**，主要仍依靠模型行为与提示词；直接使用 API 时，可以设置 `max_uses`，但这是每次 API 请求的上限，不是整段开发会话的总预算。([Claude](https://code.claude.com/docs/en/advisor))

因此，“必须经过评审才能进入下一阶段”这种硬约束，应该由外部工作流保证，不能只寄希望于一句提示词。

## 五、成本上最容易被忽略的，是缓存与重复读上下文

这里有一个会明显影响你第三种判断的实际细节：

**Claude Code 当前保留主执行模型的缓存，但 advisor 自己读取完整对话的过程不使用缓存，每次咨询都会重新处理完整历史。** 直接调用 Claude API 则另有 advisor 侧 `caching` 选项，需要单独开启，不能把执行模型的缓存当作顾问也已经缓存。([Claude](https://code.claude.com/docs/en/advisor))

这意味着：

> “强模型只给意见、不写代码”，不代表它必然便宜；它可能正在反复进行昂贵的上下文读取。

以 Fable 5.1 官方价格作一个**仅比较输入读取的算术示例**：普通输入为每百万 token 10 美元，缓存读取为 0.25 美元。同样 10 万 token，普通读取是 **1 美元**，已经命中的缓存读取部分是 **0.025 美元**。这里不包含输出、首次缓存写入及新增上下文成本，不能理解为整次任务便宜 40 倍。([Anthropic](https://www.anthropic.com/claude/fable))

因此，**继续让一个已经拥有有效缓存的强模型工作，有时可能比另请一个需要重新读取完整历史的强顾问更便宜。** 这是基于上述机制的成本推论，不是对每个任务的保证。

另一方面，你举的 Astra 与 Luna 的单价差距确实很大。按当前标准 API 档位的官方标价，单位为美元／百万 token：

| 模型 | 普通输入 | 缓存读取 | 输出 |
|---|---:|---:|---:|
| GPT-6 Astra | 10 | 1 | 50 |
| GPT-5.6 Luna | 0.20 | 0.02 | 1.20 |

输入价格相差 50 倍，输出约相差 41.7 倍。这只是对应价格档位的比较，实际还应计入缓存写入、长上下文规则及实际渠道计费。([OpenAI Developers](https://developers.openai.com/api/docs/models/gpt-6-astra))

这也意味着，**不能因为高低搭配存在沟通开销，就断言它不划算**。如果真的能把大量工作移到 Luna，同时让 Astra 很少介入，节省空间仍然很大。

我会用下面这个关系来理解三种方案：

**混用的净节省＝被替代的强模型工作成本－新增的交接、重复读取、验收与返工成本。**

而不是数“强模型调用了几次”。

## 六、社区目前怎么评价？有分歧，尚不足以支持统一排名

截至这次检索，**我没有找到在同一套真实开发任务、同样工具、相同预算与验收条件下，对 Astra/Luna 这三种模式进行完整对照的公开研究**。现有材料包括配置项目、个人经验、单项目试验和厂商内部实验，证据强度不能混在一起。

### 1. 开发者社区：不是大家都在倒向“低编排＋高实现”

GitHub 上已经有 `codex-astra-luna-orchestrator` 这类项目，采用 Astra 负责主编排和评审、Luna 负责探索与实现等工作。这证明第一种仍然有人积极实践，但该项目的配置说明本身不是端到端节省成本的对照证据。([GitHub](https://github.com/donvito/codex-astra-luna-orchestrator))

Reddit 的相关讨论里，两种体验同时存在：有人认为任务明确时 Sonnet 足够，愿意用强模型规划、便宜模型实现；也有人认为复杂工作直接交给 Opus，少几轮人工纠正，比节省 token 更重要。它们是任务背景不同的个人经验，不是可直接统计成胜率的实验。([Reddit](https://www.reddit.com/r/ClaudeAI/comments/1u7l40n/been_using_sonnet_46_on_medium_effort_and_cant/))

9 月 10 日 Linux.do 的一篇讨论，也同时主张按任务总成本选择模型、让强模型直接解决难题，以及用 Astra 搭配 Luna。至少在这类近期讨论中，争论焦点仍是**总消耗、推理强度与计划质量**，并没有形成“反向编排一定更优”的一致意见。([LINUX DO](https://linux.do/t/topic/2885553))

### 2. 有一个公开实验，与你对第一种的担忧相当一致

Akita 的一个 Rails 项目编码实验报告：

| 方式 | 报告中的评分 | 时间 | 成本 |
|---|---:|---:|---:|
| Opus 4.7 单独完成 | 97/100 | 18 分钟 | 4.04 美元 |
| Opus 规划＋Kimi K2.6 手动执行 | 97/100 | 30—40 分钟 | 估计 3—7 美元，包含规划 |

在这个任务上，混用没有体现出质量优势，耗时更长，成本也没有明确优势。不过，它只是单项目、自定义评分，而且部分费用是估计值，不能推广为所有开发任务的结论。([GitHub](https://raw.githubusercontent.com/akitaonrails/llm-coding-benchmark/master/docs/success_report.manual_orchestration.md))

它最有价值的提醒是：**不要只展示便宜工人的账单，把规划和反复协调的费用藏起来。**

### 3. 但 Cursor 的工程实验提供了另一面

Cursor 7 月 20 日公开的 SQLite/Rust 代理实验中，Opus 4.8 规划＋Composer 2.5 执行的组合成本为 **1,339 美元**，GPT-5.5 同时承担规划和执行的配置为 **10,565 美元**；新系统中的各配置最终都通过了其保留的 SQL 测试集。([Cursor](https://cursor.com/blog/agent-swarm-model-economics))

这里不能把差额全部归因于编排方式：模型组合不同，也不是固定同一个强模型进行单变量比较，更不意味着实现了完整、生产可用的 SQLite。**但它足以反驳“第一种在开发工作中必然不划算”**：在规模大、可分解、工程化程度高的工作里，它有成立的空间。([Cursor](https://cursor.com/blog/agent-swarm-model-economics))

### 4. Advisor 的测量结果也不支持“效果只能居中”

Anthropic 当前公布的内部编码测试中，**Opus 5 执行＋Fable 5.1 顾问**每次尝试约 7.69 美元，相比 Opus 5 默认设置单独执行，得分高约 **3.5 个百分点**且略便宜；相比 Fable 5.1 单独执行，得分高约 **2.5 个百分点**，但成本约为其 **1.5 倍**。对 Fable 单独执行的重复测量较少，因此后一比较要更谨慎。([Claude Platform](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence))

这说明第三种可能不是“折中档”，而是另一种成本—质量组合：**可能更准确，但未必比直接用最强模型便宜。**

我对这些材料的综合判断是：**没有哪一种组织结构天然胜出，任务结构和整个代理运行系统的影响，可能大于“谁当主代理”这个选择。**

## 七、针对你的使用方式，我会怎样搭配

我会采用一个以第二种为主、允许第三种进入、但不强求所有任务走同一条路径的方案：

**强模型确定方案与验收 → 轻量模型／程序调度 → 按任务难度执行 → 客观检查 → 关键变更由强模型复核。**

### 强模型要提前决定什么？

不仅是“做哪些任务”，还包括**哪些决定不能由执行者擅自更改**。

给每个任务的说明应包含目标、接口与不变量、相关代码入口、允许修改的范围、验收命令，以及需要返回重新规划的条件。强执行代理应能查看原始代码和证据，不应只能依赖轻量调度器的摘要。

任务粒度也不宜碎到“改一个函数就交接一次”。我会优先按**能够独立验收的一项功能或修复**划分，而不是机械地按文件数划分。

### 顾问什么时候介入？

我建议把触发点放在任务阶段和可观测事件上，而不是“每操作一次都问”：

| 触发点 | 建议处理 |
|---|---|
| 非平凡任务完成初步代码探索，准备确定实现路线 | 咨询一次强模型；已有适用方案的常规任务可跳过 |
| 同类失败重复发生、需要改变接口或推翻原计划 | 返回强模型判断；必要时直接接管实现 |
| 关键变更准备合并，已有实际补丁和测试结果 | 做针对性复核，而不是只检查执行模型的总结 |

“两次同类失败就升级”可以作为一个初始规则，但这是我建议你试验的阈值，不是经过普遍验证的最佳值。

最重要的是：**咨询次数需要有预算，咨询后也要有接管出口。** 不要让廉价模型在强顾问帮助下无限尝试。

### 还有一个必须比较的第四种基线

**强模型单代理＋适当降低推理强度＋保持有效缓存。**

它没有跨模型交接，也没有多代理之间的信息传递损失。Anthropic 的成本优化测量也明确提醒：某些看似比默认强模型便宜的多模型配置，仍然比同一强模型降低推理强度后的单代理方案更贵，因此应先测这条基线。([Claude Platform](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence))

这不代表所有难题都应低强度运行，而是不要把“强模型＋最高思考档＋不限重试”当成唯一的单模型对照。

## 最后的选择

**在你的前提下，我赞成优先测试第二种，但理由不是“轻量模型适合管理强模型”，而是“真正困难的规划已经提前完成，剩下的调度不值得继续支付高价”。**

我的条件化选择会是：

| 你的主要任务特点 | 我会优先尝试 |
|---|---|
| 计划成熟，任务边界明确，实现本身较难 | **② 轻量调度＋强实现** |
| 大部分步骤常规，只在少数决策点卡住 | **③ 轻量实现＋强顾问，并允许强模型接管** |
| 大量独立、重复、可客观验收的工作 | **① 强规划／编排＋轻量实现** |
| 高度耦合，需要持续探索与重新判断 | **强模型单代理，先优化推理强度和缓存** |

真正做对照时，我会看**每个合格交付的总成本、首次验收通过率、漏掉的问题、人工修复时间和总耗时**，而不是看某个代理的账单。前期规划、顾问调用、失败尝试、缓存读写都要算进去；使用订阅或第三方渠道时，则以真实账单和额度消耗为准。

**你的直觉中最值得保留的一点，是不要让昂贵模型一边付出完整理解成本，一边反复监督一个不能独立完成任务的执行者。进一步优化的方向，不是固定让谁当“老板”，而是让每一次昂贵判断都真正结束一段不确定性，而不是开启下一轮沟通。**

## 7. AI

**我更认可这套方案。它比固定的“强编排＋弱实现”或“弱编排＋强实现”更适合作为长期使用的开发架构。**

你实际上已经把问题从“谁当主代理最好”，转变成了：

> **提供不同成本、能力和权限的服务，让每项工作选择合适的执行方式。**

不过，我会给“自由组合”加一个限定：**模型组合可以自由，任务边界、升级条件和成本约束不能完全自由。** 否则，虽然可选方案变多了，主代理也可能花更多时间判断、沟通和反复切换。

我的建议是：**保留你的四类服务，再补上“主代理直接完成”这一条路径，以及一套尽量简单的调度规则。**

## 一、你这套方案最有价值的变化，是加入了“中档执行者”

上一轮三种模式，隐含了一个比较极端的二分：便宜模型做，或者最强模型做。

加入中档后，就不必总在“让轻量模型反复尝试”和“直接支付最高档费用”之间选择。我会优先把中档作为**常规实现工作的候选默认档位**，再用实际任务验证这个选择，而不是要求所有实现先从最便宜的模型开始。

同时，你的四类服务实际上分属两个维度：

**前三类是执行能力分档；第四类是职责和权限不同的顾问角色。**

我会这样定义它们：

| 服务 | 核心职责 | 需要明确的边界 |
|---|---|---|
| **轻量工作服务** | 定向检索、收集证据、执行既定测试、整理日志、机械修改 | 不独自作重要架构决策，不把“没找到”当成“不存在” |
| **常规实现服务** | 根据相对明确的需求，独立完成实现、测试与局部修复 | 遇到接口变更、方案失效或持续不收敛时，返回升级请求 |
| **高阶执行服务** | 复杂诊断、困难实现、跨模块修改、接管卡住的任务 | 对交付负责，不只是提供一个思路就结束 |
| **高阶顾问服务** | 评估方案、诊断方向、审查关键变更、指出遗漏 | 默认不修改代码；信息不足时能请求或读取原始证据 |

这种“角色、模型、工具权限分别配置”的方式也符合现有代理框架的能力。例如 Claude Agent SDK 可以为子代理分别指定模型、提示词和工具，并支持只读评审与可执行测试等不同权限组合。([Claude](https://code.claude.com/docs/en/agent-sdk/subagents))

**所以，“高阶执行者”和“高阶顾问”即便用同一个模型，也值得保留为两个入口。** 区别不在于换了一个名字，而在于前者接受的是“把这件事做完”，后者接受的是“解决这个判断问题”。

但它们应当是**按需选择的服务池，不是每个任务都必须经过的四道工序。**

## 二、“不限制主代理档位”是对的，但主代理承担的判断不能不受限制

这里我赞成你的设计，不过要区分两句话：

**“任何档位都可以当主代理”——可以。**

**“任何档位当主代理，都可以承担同样复杂的决策”——不能直接这样假定。**

我会根据主代理当前需要做的工作来选档位，而不是根据它拥有多少强力子代理来选。

### 计划成熟时，轻量主代理有合理的位置

任务边界、依赖关系、验收标准都已经确定，主代理主要负责领取任务、分派、等待、记录结果和触发检查。此时可以试用轻量模型，其中一部分流程甚至可以直接由程序控制。

但计划应该包含**“出现什么情况需要重新规划”**。否则，执行者发现新约束后，轻量主代理可能仍然继续按旧计划派工。

### 需要持续决策时，强主代理仍然有价值

需求还不清楚、多个模块相互影响、实现过程中不断出现新事实——我不会为了追求形式上的低成本，强行让轻量模型继续主持。

一个需要防范的失败路径是：

> 主代理拆错任务 → 强执行者忠实完成错误任务 → 主代理按错误标准验收。

这个问题不能靠“子代理足够强”自动消除。

因此，我建议给弱主代理设置**决策升级边界**：改变公共接口、推翻既定方案、调整跨模块依赖、放宽验收标准时，必须找高阶顾问或返回人工确认，而不是自行决定。

Anthropic 对路由工作流的适用条件也有类似限定：任务应当存在可区分的类别，而且分类本身需要足够准确；并不是增加几个模型选项就自然实现了有效路由。([Anthropic](https://www.anthropic.com/engineering/building-effective-agents))

### 强主代理也不应被迫委派

这是我觉得你需要明确补上的一条：

> **主代理已经充分理解上下文，而且能直接完成一个短任务时，允许它自己完成。**

不要出现“强模型已经知道该改哪三行，但为了使用资源池，先写任务说明，再让另一个模型重新理解”的情况。

**能委派，不等于应当委派；强＋强也应有明确目的，例如隔离独立任务、并行探索或提供另一轮检查，而不是默认套一层。**

## 三、我会调整“粗任务用轻量模型”这个分类

这里最容易误判的，是把**工作量大但看起来不起眼**的事情，当成认知难度低的事情。

“调研”和“测试”都不是天然的低难度标签：

| 工作 | 我建议的起点 |
|---|---|
| 查找指定接口的调用位置，返回文件与代码依据 | 轻量 |
| 判断哪些调用关系真正影响本次改动 | 中档起，复杂时高阶 |
| 运行已经确定的测试命令，收集失败日志 | 程序优先，轻量辅助 |
| 为一个陌生模块设计有效测试，判断覆盖是否充分 | 中档或高阶 |
| 根据明确规则批量修改配置 | 轻量或中档 |
| 判断一项变更会不会破坏跨模块不变量 | 高阶候选 |

这些是我建议的初始路由，不是具体型号的能力保证。

尤其是调研，我会要求轻量代理返回**证据，而不仅是结论**：

“相关文件、对应代码位置、搜索过的范围、未确认的问题”，比一段“我已经调查清楚了”的总结更有价值。

后续实现者和顾问必须能查看原始代码，不能只能通过轻量模型提供的信息来理解问题。否则，廉价调研阶段漏掉的关键约束，可能会影响后面所有昂贵判断。

同样，**“测试执行便宜”不意味着“正确性判定便宜”**。我会把运行测试交给程序，把测试充分性、需求一致性等判断单独处理。

## 四、顾问与高阶执行者之间，需要一个明确的“接管规则”

这是混合方案中最值得设计好的接口。

我的判断标准很简单：

> **缺的是一个关键判断，就咨询；缺的是独立完成任务的能力，就接管。**

例如，常规执行者不知道应该修改调用方还是被调用方，但一旦方向明确，剩下的实现能做好。这适合调用顾问。

反过来，顾问已经解释了并发状态应该怎样处理，执行者仍然反复写错，那就应该让高阶执行者接手，而不是继续增加顾问轮次。

**不要把“高阶顾问”用成一个只能口述补丁、却不能亲自完成任务的高阶程序员。**

### 我建议的触发方式

不要只靠执行模型自报“我不确定”，也不要要求每次修改前都咨询。可以采用三个触发点：

**决策前触发：** 初步探索后，发现涉及关键接口、跨模块约束或高风险变更，而现有方案没有覆盖。

**停滞时触发：** 同类失败重复发生，或者已经消耗了预定尝试预算，却没有新增有效证据。

**交付前触发：** 特定重要变更必须经过独立评审，不能因为实现者认为没问题就跳过。

对于初始版本，我会先试验“同一个阻塞点咨询一次，应用建议后仍不收敛就考虑接管”的规则。这只是起始策略，不是普遍最优阈值；环境损坏、需求缺失等问题，则应先补条件，不能一律靠升级模型解决。

### 自建顾问服务，可以比原生 advisor 更灵活

当前 Claude 原生 advisor 接收执行者完整对话，本身没有工具，也没有独立的上下文管理。([Claude Platform](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool))

你自己提供顾问子代理服务，就不必照搬这个机制。我更倾向于：

**先给它明确问题、必要事实、相关代码入口和失败证据，再允许它按需只读检查。**

这样既不必默认搬运整段开发历史，也不必让顾问只能相信调用者的摘要。不过，这只是更可控的上下文设计，**不保证每次更省钱**：顾问自行探索同样会产生开销，需要限制范围和预算。

当顾问已经深入理解问题、接近能够直接修复时，还应允许把已有任务状态交给高阶执行者，避免完全从头再来。

## 五、真正决定这套系统能否省钱的，是四个运行约束

### 1. 允许跳级，不要求“轻量失败后才能用高级”

我不会把三档执行者实现成固定的“轻量→中档→高阶”流水线。

明显复杂的任务，可以直接交高阶；普通实现可以直接交中档。便宜模型的失败尝试也是成本，不能因为单次便宜就视为免费。

更合理的目标是：

**在满足质量要求的前提下，选择预计总成本较低的路径，而不是选择当前单次调用最便宜的模型。**

### 2. 默认一层委派，顾问调用单独受控

初期我会让主代理分派任务，执行者可以提出咨询或升级请求，但不允许所有代理无限创建下一层代理。

否则很容易从你的四类服务，演变成“中档执行者又创建轻量调查者、再创建高阶顾问、顾问又启动另一轮调查”的难以追踪的调用链。

深度、并发、重试、顾问次数和总花费，应由运行程序检查，而不仅写在提示词中。现有 Claude Agent SDK 已提供子代理深度、并发和预算限制；跨厂商资源池仍需要统一汇总所有调用的用量。([Claude](https://code.claude.com/docs/en/agent-sdk/subagents))

### 3. 交接传成果与证据，不传整段工作聊天

我建议任务交接至少保留：任务目标、方案版本、关键约束、当前代码版本、补丁、已执行检查、未解决问题。

主代理默认只接收摘要和这些成果的位置，必要时再深入读取；完整日志保留在外部，不要每次都塞进主代理上下文。

Anthropic 的多代理工程总结也提出了类似做法：让子代理把成果保存在外部，向协调者返回轻量引用，以减少层层转述的信息损失和重复传输开销。([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system))

这里还需要一个简单原则：**同一项修改有明确的执行负责人。** 并行修改使用隔离工作区，合并后再运行集成检查，不让多个执行者同时无约束地改同一份代码。

### 4. 预算不能只算执行者

主代理的协调、顾问读取、失败尝试、重新规划、验收和人工修复，都应进入任务账本。

否则你很可能看到“中档执行者只花了一点钱”，但主代理为了管理它付出的成本已经超过了节省额。

我会尤其关注**协调与评审开销占比**：它持续上升时，应优先检查任务是否拆得太碎、上下文是否反复搬运，而不只是继续换更便宜的执行者。

## 六、我的默认起步配置与验证方式

按照你的思路，我会从下面这套配置开始试验：

**中档主代理，小任务自行完成；轻量服务负责定向证据采集与测试执行；中档子代理负责独立的常规实现；高阶执行者处理明确难题；高阶顾问处理关键判断和指定评审。**

当需求模糊、全局耦合强时，升高主代理档位；当计划成熟、工作主要是派工和检查时，再尝试降低主代理档位。

这不是把主代理固定在中档，而是给系统一个可测量的默认值，避免每次都从零决定整套组织方式。

验证时，我会拿同一批有代表性的任务，对比**中档单代理、强模型单代理、你的混合方案**，保持验收要求一致。重点看完成率、每个合格交付的总成本、人工介入和总耗时，而不是某一次调用用了什么模型。OpenAI 的代理构建指南也建议先建立高能力模型的性能基线，再逐步替换为较小模型，检查质量是否仍然达标。([OpenAI](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/))

**最终，我认为你这套方案值得做，而且方向比固定押注某一种“高低搭配”更合理。它的优势是可以按任务选择路径，不是因为同时用了四种角色就必然更强、更便宜。**

我会用一句话概括它应当遵守的原则：

> **自由选择模型，但减少无意义交接；顾问负责解决判断问题，执行者负责交付；一旦低成本路径不再收敛，就及时换路径，而不是维护原来的分工形式。**
