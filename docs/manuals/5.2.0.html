fable-advisor 5.2.0 版本说明书

自包含中文说明书。进仓库、不随插件目录发布。第一部分说明本版装上之后的完整行为；第二部分列出相对 5.1.0 的每一条改动。

5.2.0 仍是角色池加姿态：任一模型都可以当主代理；一次派发是一个角色、一个档位、一条车道。本版让报告模式能在已有未提交改动的工作树上跑完，给 CLI 会话一个可读标题，把用户级正典交给伴生安装器写入活体，并把 senior 从首轮选择里拿掉、只经升级梯或用户声明到达。填充表的型号排序属于用户路由档案，不是插件行为。

1. 角色 × 档位 × 车道 × 姿态

这四轴互相正交。角色回答契约形状，档位回答能力等级，车道回答如何到达供应商，姿态回答主代理会不会亲手改交付物。型号不写进插件技能正文。

角色

角色权限返回
explorer只读证据：file:line、符号、原文
worker在契约的 Files 内可写diff 与验证证据
advisor只读不超过 300 词的 verdict。两种请求形状：决策（动工前）与验收（完工后：契约 + diff + receipt）

角色不含模型型号。卡住任务的接管是 worker 加一份接管契约，不是另一个角色。

档位与首轮池

档位是 light / standard / senior，与角色正交。任一角色可派任一档位。

light 与 standard 构成首轮档位：两档按第一段对判断依赖的评估自由选择，没有失败前置。senior 只经升级梯的门或用户声明到达；插件不把「代价高就直派 senior」写成第一段规则。

拨盘是档位在车道内的实现：型号加 effort。记法见第 2 节。格内取值写在用户路由档案，见第 12 节。

车道

车道回答怎么到达供应商。handoff lane 是条件成员：只有用户按任务或按会话声明之后，才进入第二段候选。

grok laneGrok 家族Claude Code：plugin/scripts/run-grok.mjs。Cursor：钉 Grok 型号名的 Task；medium / high 也可经 Shell 跑同一 runner。
codex laneGPT 家族两侧都跑 plugin/scripts/run-codex.mjs。Cursor 经 Shell。Cursor 侧没有 receipt gate，失败时放行。
claude laneClaude 子代理仓内九份 agent 文件，无外部 CLI。同模派发是它的一个拨盘：模型钉为会话模型。Cursor：generalPurpose 省略 model（inherit）。Claude Code：worker-* 的按次 model 设为会话模型。
handoff lane用户中介写入 .fable-advisor/handoff/<slug>.md。无 receipt、不在 receipt gate 视野内。验收是 diff，由架构师亲自重跑验证。

cursor lane 只在 Cursor 宿主存在，见第 8 节。它不进技能正文的车道表。

姿态

编排姿态主代理不亲手改交付物：写交付契约、派 worker、验收。职责名：架构师。没人声明时，存在上游任务件（issue、spec、task）即为此姿态。
实现姿态主代理可亲手改交付物，同时仍可派任一角色。没人声明且无上游任务件时为此姿态。

选择器顺序：用户声明或上层指示优先；二者都没有时，看有没有上游任务件。模型身份不选姿态。姿态相对一次派发成立：车道对自己的契约是实现姿态，对它再派的子代理可以是编排姿态。深度不限。Claude Code 把子代理嵌套上限订在主会话之下三层。

编排姿态下，交付物只经 worker 改，与改动大小无关。协调件（任务件、ADR、词表、工作流状态、发布版本字段）任一姿态下主代理都可直接写。本仓路径映射写在 AGENTS.md。类别不明按交付物处理。

2. 两段式路由与拨盘记法

主代理持有需求、分解、契约、路由与验收。一次派发先选（角色, 档位），再在该格的填充表里做帕累托选择。

第一段

角色按产物：证据走 explorer，改动走 worker，承诺或验收走 advisor。档位在首轮池的 light 与 standard 之间，按「契约抓不住的判断有多少」自由选择，无前置条件。senior 只经第 3 节的 senior 门或用户声明。

第二段

在该格的候选里，按用户档案声明的速度、价格、能力、专长做取舍。专长只打破平手，不推翻第一段。没有任何声明时，取最便宜且够用的候选，车道之间按各车道默认拨盘比较，不把某车道更便宜的型号或更低 effort 提前拿来比。

某条车道不可用或超时：同一格换另一个填充，并披露。两条 CLI 车道都不可用时落到 claude lane，并说明失去的跨厂商复核。可用性由这次派发的结果决定，不靠事先探测。

记法 model[a*, b, c]

拨盘写作 model[a*, b, c]：方括号里是这一格、这一型号可选的 effort，全部属于首轮，* 标默认。没有 effort 维度的型号裸写（例如 haiku-4-5）。已退役的 |（仅升级）记法不再使用。

档案里的具体型号排序是用户判断，见第 12 节。本节只说明机制。

3. 升级梯 R1–R4 与 senior 门

规则含义
R1验收未过：返工票，同会话、同拨盘。契约缺口：修正后的契约，仍回同一条车道会话。
R2返工票也未过，且归因为能力：一次提升。新会话，接管契约 = 原契约 + 上轮报告 + receipt。一次提升要么同型号升 effort，要么换型号。
R3同一型号最多提升一次。再提升必须换型号，除非更高各格里没有别的型号。
R4执行时出现较大问题（工具反复失败、跑飞、触碰保留项）可跳过返工票，直接换型号，记一次失败。

senior 门：首轮池内两次能力归因的失败，或用户声明。两次失败指：原拨盘的返工票失败，换型号重派后再失败。这与决策类型门的「同一问题两次失败」重合；advisor 的 verdict 顺带裁定是否上 senior。

提升跑在接管契约下：那是契约形状，不是档位。契约缺口的路径不走升档：修正契约，仍回同一车道会话。

4. 决策类型门与验证三层

决策类型门约束任何主代理、任一档位、两种姿态。它是技能正文规则，不是 hook。到点位咨询 advisor 的决策形状：传入决定、约束、备选；advisor 自己读代码。对 verdict 采取行动，或公开分歧；不得静默忽略。没有机械强制，也没有逐 diff 过审。

  • 承诺一种架构、数据迁移、API 形状或重构策略
  • 推翻既定方案
  • 改公共接口或跨模块依赖
  • 放宽验收标准
  • 同一问题两次失败

advisor 的验收形状由验证第 3 层到达，不按步数触发。从 5.1.0 起，「宣告多步交付物完成前」不再是门的一项。

报告是声称，不是证据。审查对象是契约。三层：

层级何时做什么
第 1 层每条车道默认接受车道的验证证据（命令、退出码、输出尾、对照工作树抽查）加上 git diff --stat。完整无范围的 git diff 不进主代理上下文。
第 2 层报告、git diff --stat 或验证输出引起具体怀疑读路径范围的 git diff <file>。车道自己写的验收测试是声称的一部分，要读它。
第 3 层正确性关键、同族 diff、或用户要求评审advisor 以验收形状读 diff 与 receipt，返回 verdict 与标出的片段。同族 diff 优先换跨厂商填充。verdict 仍是声称，终裁在主代理。

「应该能工作」「测试应该过」或没有命令输出的报告，都不算完成。

5. 五部交付契约与两份前言

车道不共享主代理上下文。每次派发携带五部：

部键内容
1. Objectiveobjective结果与验收标准，不是步骤
2. Filesfiles授权范围（路径或目录）；范围内新建文件允许
3. Interfacesinterfaces结果必须匹配的共享或外部契约；可以为无
4. Constraintsconstraints保留项：不得改什么、上游已钉死的选择、调用方留在自己会话里的操作。约束车道、其子代理与其验证命令
5. Verificationverificationworker：其输出即验收证据的命令，至少一条在目标未达成时会失败。explorer / advisor：期望的证据或 verdict 形状，可为空

Constraints 未钉死的实现选择归车道：不上报、不等待。契约缺口（预期行为不明、要求冲突、必须改保留接口、无法判定什么算通过）上报，由架构师修正契约。

存在上游任务件时，契约引用其路径，只内联验收标准、保留约束与验证命令，并标明哪些节有约束力。主代理不重述、不重规划。

返工票是给同一车道的新契约，复用其会话：Objective 写缺陷（违反的要求、可复现失败、期望行为、证据）；Files 仍是原范围；Verification 是失败的那条检查。票内不写修复方案。

两份前言

前言是执行侧契约的单源，与 runner 同目录解析：<plugin-root>/skills/orchestration/。当前 mode 所需前言缺失时，runner 退出非零、不拉起子进程，stderr 指名文件；不写 receipt。

文件用于执行侧约定
lane-preamble.mdmode: implement（缺省）执行者持有 Files 内的交付物。保留操作仍约束它及其子代理。以 WORKER REPORT（OBJECTIVE / CHANGES / VERIFIED / GAPS）结尾。
lane-preamble-report.mdmode: report只读的 explorer 或 advisor。Files 是读取范围，不是写权限。回答 Objective。explorer 以证据形状结尾，advisor 以 verdict 形状结尾。不含 WORKER REPORT。

Cursor 的 Task 不会自动前置前言。worker 派发的 prompt 首行指向 lane-preamble.md；explorer / advisor 派发的 prompt 首行指向 lane-preamble-report.md。不要在契约正文里复述前言。

6. 两条 runner：spec、receipt、错误类与报告模式

主代理把五部写成 JSON，放到目标仓 .fable-advisor/pending/<slug>.json，然后跑 runner。车道在 runner 进程退出时结束。receipt 打印到 stdout，并写入 .fable-advisor/receipts/<spec_hash>.json。error_class: complete 时 runner 自己删除 pending spec。

node "<plugin-root>/scripts/run-codex.mjs" --spec .fable-advisor/pending/<slug>.json --cwd "$(pwd)"
node "<plugin-root>/scripts/run-grok.mjs" --spec .fable-advisor/pending/<slug>.json --cwd "$(pwd)"

未知顶层键或越界值记 spec_invalid，永不静默改写。CLI 车道验收 = error_class: complete + 非空会话 id + 可对照工作树抽查的验证输出 + 技能正文的分层验收。引用 receipt 里的型号或 effort 时写「已提交，未观测」：那是 runner 提交给 CLI 的值，不是从运行事件读回来的。

spec 键

五部键：objective、files、interfaces、constraints、verification。implement 模式 verification 至少一条；report 模式可以为空数组。files 在 report 模式是读取范围，也可以为空。

键codexgrok
modeimplement（缺省）或 report。其他值 → spec_invalid
model白名单 gpt-6-astra（缺省）、gpt-5.6-luna、gpt-5.6-sol。名单外 → spec_invalid可省略：省略则不传 -m，由 CLI 默认目录决定。目录可读时按目录校验；目录不可读时跳过校验，由实跑决定可用性，不是 grok_unavailable
effortlow | medium | high | xhigh | max。省略时按型号：astra → medium，luna → max，sol → highlow | medium | high | xhigh。省略则不传 effort 旗标，CLI 用自己的默认；receipt 记提交值（省略为 null）
title可选非空字符串。prompt 第一行是标题原文（纯文本，不加 Markdown 标记），空一行，再前言，再五部。省略时第一行是 spec 文件去掉 .json 后的文件名。空串或非字符串 → spec_invalid、不拉起子进程
service_tier可省略；合法值只有 fast不是 spec 键
idle_timeout_sec静默截止，缺省 600。只切「最后一次事件之后的沉默」，跳过验证
timeout_sec整次运行的绝对上限。无缺省；省略则不封顶
resume_session_id上次的 codex_session_id；调用 codex exec resume <id>上次的 grok_session_id；传 --resume <id>

白名单与回退

codex 目录是静态白名单。启动前回退只保留 astra → luna：条件是 resume_session_id 为空、请求型号是 gpt-6-astra、且首次结果为 preparation_stalled，或 codex_failed 且尚无会话 id。回退后 receipt 为 model_requested: gpt-6-astra、model_used: gpt-5.6-luna、fallback_reason 非空（值为第一次的错误类）。会话一旦建立不再回退。gpt-5.6-sol 与 luna 一样不回退：点名 sol 失败时 model_used 仍是 sol，fallback_reason 为 null。

grok 车道没有型号回退，fallback_reason 恒为 null。不要预先探测 CLI 登录态；最多检查安装（which grok）。可用性以 receipt 为准。

receipt 字段

两条 runner 都写：receipt_version、mode、report（仅 report 模式带 CLI 最终消息，implement 为 null）、spec_hash、cwd、producer（codex 或 grok）、model、model_requested、model_used、fallback_reason、effort、resumed_from、end_to_close_ms、max_idle_ms、idle_timeout_sec、timeout_sec、started_at、finished_at、exit_status、error_class、dirty_baseline、changed_files、verification。

codex 另有 service_tier、codex_session_id、codex_final_message。grok 另有 grok_session_id（runner 注入 --session-id）、stop_reason、usage、total_cost_usd、grok_final_message。

dirty_baseline：拉起 CLI 之前跑一次 git status --porcelain。非空为 true，空为 false，这次 git status 本身失败为 null 并继续。两条 runner、两种模式都记。运行后的 git status 失败仍是 git_status_failed。

end_to_close_ms 与 max_idle_ms 是诊断，不是门。

错误类

共享：complete、spec_invalid、preparation_stalled、idle_timeout、timeout、interrupted、verification_failed、no_diff、unexpected_diff、empty_report、git_status_failed。

codex 另有 codex_unavailable（PATH 上没有 codex）、codex_failed。grok 另有 grok_unavailable（拉起进程得到 ENOENT）、grok_failed。

no_diff：implement 模式且 files 非空、运行后无改动；pending 文件留下。普通 spec 要调查；返工票上这可能表示缺陷无法复现。idle_timeout 与 timeout 表示时钟切断，跳过验证；恢复路径是带该 receipt 会话 id 的返工票（resume_session_id），不是主代理手验工作树。

implement 模式应先有干净工作树：git status --porcelain 为空。开跑前已有脏文件时，空跑会看起来像做了工作。implement 的 no_diff 与 git_status_failed 语义相对 5.1.0 不变。

报告模式语义与脏基线规则

  • CLI 以只读工具集运行。codex 为 --sandbox read-only。
  • 前言用报告前言，不用 worker 前言。
  • 工作树没有被本车道弄脏，是正常结果，记 complete。receipt 另带 mode 与 report。
  • 开跑前干净、跑完变脏：unexpected_diff，不是 complete。
  • dirty_baseline: true 时不判 unexpected_diff。empty_report 与 complete 仍按原规则。changed_files 仍记录运行后观察到的路径。此时只读工具集是唯一防线。
  • dirty_baseline: null（开跑前 git status 失败）不满足「为 true 则跳过」，跑完若观察到改动仍会判 unexpected_diff。
  • 工作树干净但收集到的报告文本为空或只有空白：empty_report，pending spec 留下。
  • 报告模式判定顺序：先 unexpected_diff（本车道弄脏的树），再 empty_report，再 complete。
  • receipt gate 对报告模式的 pending spec 同样生效。

7. claude 车道的九份 agent 文件

一份文件对应一个（角色, effort）。以 fable-advisor:<name> 派发。文件名与 name: 用缩写（l / md / h / xh）；文首字段 effort: 写全称。effort 没有按次参数：文件钉死 effort，按次 model 选择填充。

不要传 name（具名队友）：传了则文首字段 effort: 被忽略，静默落到该型号在 ~/.claude/settings.json 里的档位。省略 name 才是后台子代理，文首 effort 生效。

agent 文件只在会话启动时加载。中途新增或改名会得到 Agent type '<name>' not found。改池之后必须重启会话。

解析顺序：按次 model → 文件的 model: → CLAUDE_CODE_SUBAGENT_MODEL → 主会话模型。内置 Explore 仍可用作 light explorer，但没有自己的 effort；省略 model 时跑会话模型（Claude API 上限 Opus）。

插件不固定 advisor 的缺省拨盘。缺省写在用户路由档案：决策形状用 standard 格，验收形状用 light 格；落到哪份 agent 文件由该格所选拨盘的 effort 决定（advisor-l / advisor-md / advisor-h / advisor-xh）。

没有 explorer-l：haiku 没有 effort 维度，light explorer 用 explorer-h 加按次型号。从 Claude 主代理派本车道时须披露：同族（没有跨厂商复核）、共享 Anthropic 额度。Fable 作为 advisor 走用量额度，账户需要先启用。

8. Cursor：钉派发、cursor lane、runner 经 Shell、用户级门禁

Cursor 经 Claude 插件兼容路径加载本插件。grok lane、claude lane 与 cursor lane 是原生 Task 派发，各自钉模型。codex lane 不在 Task 枚举里。

钉模型的 Task

  • worker：generalPurpose + 显式 model，prompt 首行指向 lane-preamble.md。
  • explorer：explore（或 generalPurpose）+ 显式 model，prompt 首行指向 lane-preamble-report.md。
  • advisor：具名 advisor-* agent，显式钉模型，prompt 首行指向报告前言。

钉的家族就是车道：Grok 家族是 grok lane，Claude 家族是 claude lane，Cursor 自家模型是 cursor lane。cursor lane 只在 Cursor 宿主存在。插件 agent 的文首字段 model: 在 Cursor 对插件加载的 agent 不生效；省略 model 会继承会话模型。Cursor 不向主代理回传执行元数据，披露时标「已请求，未确认」。effort 钉在型号名上；档案里的 model[…] 在这里映射为型号名变体。用本轮允许名单里的活型号名，不要用技能示例里可能缺席的名字。

同模派发是唯一允许省略 model 的派发：编排姿态下的准则散文，generalPurpose 继承会话模型。披露里写 inherit，以免被当成漏钉。验收走技能正文的三层；Task 派发没有 receipt。

返工用 Task resume 加上返工契约。再失败则按升级梯归因。竞赛用隔离工作树的派发类型（当前枚举里的 best-of-n-runner），每名选手自己的分支与工作目录。

codex / grok runner 经 Shell

GPT 家族：node "<plugin-root>/scripts/run-codex.mjs" --spec … --cwd "$(pwd)"，经 Shell。spec、pending/receipt、等待协议、resume_session_id、mode: "report" 与 Claude Code 相同。两处不同：没有 receipt gate（Cursor 是否加载插件 Stop hook 未经核实，本车道按不加载设计，与 handoff 同一安全级）；等待跟 Shell 时钟，长票后台跑、按 shell id 等。

grok runner 同样经 Shell：node "<plugin-root>/scripts/run-grok.mjs" --spec … --cwd "$(pwd)"，同一套 spec、pending/receipt 与等待协议，同样没有 receipt gate。尚未在 Cursor 实跑。

用户级门禁与钉模型规则

lane family gate 是用户级 preToolUse 脚本 cursor-hooks/fable-lane-family-gate.py（活体 ~/.cursor/hooks/fable-lane-family-gate.py）。它守「静默继承会话模型」，不查家族。对 advisor- 前缀的 subagent_type，model 缺失、空串或 inherit 则 deny。resume 跳过型号检查。explore / generalPurpose 不在此门范围内。空 stdin 则 deny。不是插件 hook，也不扩到未标记的 worker。

钉模型规则是用户级 Cursor 规则 cursor-hooks/fable-lane-pin.mdc（活体 ~/.cursor/rules/fable-lane-pin.mdc）：提醒每次显式钉允许名单里的型号名；省略 model 的 generalPurpose 是同模派发，不是厂商车道。

10. receipt gate

插件 Stop hook，针对主会话自己：排了 spec 却不跑、或把非 complete 的 receipt 当完成。实现是 plugin/hooks/hooks.json 调 plugin/hooks/receipt-gate.py。

  • 扫描 <cwd>/.fable-advisor/pending/*.json。按 spec 文件 sha256 找 .fable-advisor/receipts/<digest>.json。
  • 没有 receipt，或 error_class 不是 complete：stderr 列出 pending 文件，退出 2，拦住结束。
  • 没有 pending 目录：放行。
  • stop_hook_active 为真：放行，避免重入。
  • stdin 不是合法 JSON：失败时放行（退出 0）。没有 python 运行时：hook 包装同样失败时放行并在 stderr 说明。

门禁只强制 receipt 存在且为 complete；内容仍由主代理判断。放弃或改道时要亲手删 pending 文件并说明，不能只靠这扇门。handoff 目录在 .fable-advisor/handoff/，故意不在此视野内。Cursor 经 Shell 的 runner 按无此门设计。

12. 路由档案

填充表是（角色, 档位）→ 候选车道与拨盘的有序表，属于用户判断，不是插件行为。插件技能只规定：调用方指令点名哪份档案就读哪份；首次分配模型前读；档案变化或滑出上下文时重读；未指定或读不到则报缺口、不假定内容。

角色路径
正典（唯一编辑源）docs/agents/fable-advisor-routing.md
活体（技能实际读取、由调用方指名）~/.claude/docs/fable-advisor-routing.md
中文备份（不安装）docs/agents/fable-advisor-routing.zh.md

结构：声明日期与锚定模型 → 首轮池说明（前两列自由选，第三列有门）→ Claude Code 表 → Cursor 表 → 升级梯引用（指向技能，不复述梯子）→ 资源偏好（含基准数据与声明日期）→ 调整方法。advisor 的缺省也在档案里：决策形状用 standard 格，验收形状用 light 格；agent 文件跟着所选拨盘的 effort 走。

表头形状是角色 ×（light / standard / senior 有门）。格内拨盘用 model[a*, b, c]。Cursor 表按机制映射同一份取值：GPT 行经 codex runner（Shell）；grok 的部分 effort 经 grok runner（Shell），其余可钉本轮允许名单里的型号名；Claude 行只取本轮允许名单有的型号名变体；Cursor 自家模型走 cursor lane。型号名来自该轮允许名单，档案不持久化可能过期的型号名。缺席的变体跳过，并在披露里说明。

易变状态（额度、截止日期）只在开场口头声明，只对当次会话有效，不落盘。handoff lane 只在用户按任务或按会话声明后进入候选。

如何调整

  1. 只改正典里的格子。中文文件是译文，不是第二编辑源。
  2. 从仓库检出跑伴生安装器，刷新活体。本机：python3 scripts/install-user-level.py --home ~ --home /mnt/c/Users/Shy。--check 只报告漂移。
  3. 不必改技能正文，也不必改插件。技能在档案变化时重读。改表时更新文首声明日期。

本说明书不复述档案里的型号排名。那些排序是用户在声明日写下的判断，随格子而变。

13. 相对 5.1.0 的改动点

5.1.0 基线提交为 83ce044（2026-09-16）。5.2.0 是次版本：runner 契约与技能正文语义向后兼容。下面每一条写改了什么、为什么、依据。

脏基线 dirty_baseline

改了什么两条 runner 在拉起 CLI 前跑 git status --porcelain，receipt 增加布尔字段 dirty_baseline（失败为 null）。报告模式且开跑前已脏时不判 unexpected_diff。implement 模式的 no_diff / git_status_failed 不变。「先干净再派」只约束 implement。

为什么5.1.0 用运行后的 git status 判改动，报告模式把任何脏树都打成 unexpected_diff。主代理因此拒绝在未提交工作树上派 grok / codex explorer，只读调查被逼去 claude 内置 explorer，丢掉跨厂商复核。

依据ADR 0018 决策 1；工单 01。

title 键与 [fable-advisor] <slug> 退役

改了什么spec 新增可选顶层键 title。prompt 第一行是标题原文；省略则用该 spec 文件短名。旧的 [fable-advisor] <slug> 行删除。receipt 不为此新增字段。Cursor Task 已有 description，不加标题句。

为什么5.1.0 每条 CLI 车道的 prompt 都以同一段前言开头，codex / grok 会话列表按首行显示，全部是同一句话，回看与续跑时无法分辨。

依据ADR 0018 决策 2；工单 01。

报告前言 lane-preamble-report.md 与内联覆盖段删除

改了什么implement 前置 lane-preamble.md；report 前置新文件 lane-preamble-report.md（只读、Files 是读取范围、回答 Objective、以证据或 verdict 结尾、不含 WORKER REPORT）。runner 内联的报告模式覆盖段删除。任一前言缺失即非零退出、不拉起子进程。Cursor 侧 explorer / advisor 派发首行改为指向报告前言。

为什么报告模式的车道以前读到的是要求持有 Files、以 WORKER REPORT 结尾的 worker 前言，执行侧契约自相矛盾。

依据ADR 0018 决策 3；工单 02。承接 role-pool-posture/issues/10。

gpt-5.6-sol 回白名单、不回退

改了什么codex 白名单加入 gpt-5.6-sol，省略 effort 时提交 high。sol 在建立会话前失败不回退到 luna。astra → luna 单跳回退保持。

为什么按档案派 sol 在 5.1.0 会 spec_invalid。用户要为即将到来的 gpt-6-sol 铺路，届时只改型号名。点名的型号只允许以失败出现在 receipt 里，不能被静默换成 luna。

依据ADR 0018 决策 4（撤销 ADR 0014 决策 11）；工单 01。

伴生安装器、两份旧规则退役、漂移测试改 --check、prompts 退出测试

改了什么新增 scripts/install-user-level.py：覆盖三件正典到活体，删除 ~/.claude/rules/fable-advisor.md 与 ~/.cursor/rules/fable-advisor.mdc。无条件覆盖。hooks.json 只警告不改。tests/test_user_level_archive.py 改为对每个存在的家目录调用 --check；prompts 仓库副本退出比对。发布流程在两侧插件更新之后加「跑安装器」一步。

为什么5.1.0 活体靠手抄，两侧仍是带「advisor (default senior)」的旧规则。手抄会漂。prompts 缺席或落后不应当让本仓测试失败。

依据ADR 0018 决策 5（修订 ADR 0011 的「活体须手动拷」）；工单 03。

首轮池与 senior 门

改了什么第一段改为：档位只在 light 与 standard 之间按判断自由选；senior 只经升级梯的门或用户声明。删除「判断很多、代价高就直派 senior 或双填竞赛」作为第一段路径（竞赛条款留在「并行」段）。角色默认 effort 句不再作为技能正文缺省。

为什么主代理频繁把任务派给最贵拨盘。模型没有判断其他模型能力的能力；用户要求把「何时上 senior」写成门，而不是留给模型临场发挥。

依据ADR 0018 决策 6；工单 04。

升级梯 R1–R4

改了什么「升级」段改写成四条：返工票 → 提升（同型号升 effort 或换型号）→ 同型号只提升一次 → 执行时较大问题可跳过返工直接换型号。senior 门与决策类型门「同一问题两次失败」重合。

为什么5.1.0 的升级叙述没有钉死返工、提升、换型号、升档的顺序，同一型号可能被连升多次 effort。

依据ADR 0018 决策 7；工单 04。

记法 model[a*, b, c] 与 | 退役

改了什么拨盘记法改为格内全部 effort 首轮可选，* 标默认。5.1.0 的 model[first-round options | escalation-only] 退役。

为什么用户要在格内按需选更高 effort，同时默认仍走便宜档。竖线把部分 effort 锁成「仅升级」，与首轮池冲突。

依据ADR 0018 决策 8（修订 ADR 0015 决策 4）；工单 04。

cursor lane

改了什么lanes-cursor.md 与词表增加 cursor lane：钉 Cursor 自家模型（如 composer）的 Task 派发。只在 Cursor 宿主存在。不把 composer 算进 claude lane，也不写进 Claude Code 填充表。

为什么Cursor 侧 explorer @ light 的首位是 Cursor 自家模型。披露时若把它算进 claude lane，会把配额与复核说错。

依据ADR 0018 决策 9；工单 04。

grok runner 经 Shell

改了什么Cursor 车道文档写明 grok runner 可经 Shell 调用，机制与 codex runner 相同（同一 spec、pending/receipt、等待协议；无 receipt gate）。标注尚未在 Cursor 实跑。

为什么档案里 grok 的 medium / high 在 Cursor 没有对应型号名变体时，只能走 runner。5.1.0 文档只写了 codex runner 经 Shell。

依据ADR 0018 决策 9；工单 04。

版本说明书制度本身

改了什么从 5.2.0 起每个发布版本有一份自包含中文 HTML：docs/manuals/<version>.html。两部分：本版完整行为；相对上一版的改动点。属交付物，进仓库、不进 plugin/、不随插件发布。发布流程在改版本号之前必须先写说明书。

为什么否则读者只能拼 ADR、工单与 diff，才能知道装上的是什么。

依据ADR 0018 决策 11；工单 07。

路由档案重写为先写后调

改了什么docs/agents/fable-advisor-routing.md 按 2026-09-16 的结构重写：首轮池说明、两张表、基准数据、末节调整方法（改格、跑安装器）。取值先落地，之后改格即生效，不改技能正文、不改插件。中文备份同步改写，仍不安装。

为什么5.1.0 档案与旧规则仍允许模型自行判断首轮上 senior，且活体落后。用户要一份能随时改格子、安装器一次刷新活体的档案，而不是改插件。

依据ADR 0018 决策 10；工单 05。

升级后要做什么
  1. 两侧都跑插件更新：claude plugin marketplace update fable-advisor，然后 claude plugin update fable-advisor@fable-advisor。Windows 侧从 WSL 经 cmd.exe 执行同等命令（先 cd /mnt/c）。
  2. 从本仓检出跑伴生安装器，刷新活体并删除两份旧规则：python3 scripts/install-user-level.py --home ~ --home /mnt/c/Users/Shy。用 --check 确认无漂移。
  3. 重启 Claude Code 与 Cursor 会话。agent 文件与插件缓存只在新会话生效。跑着的会话会继续用旧版。
