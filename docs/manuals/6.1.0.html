01

本版完整行为

01角色 × 档位 × 车道 × 姿态

这四个维度互相正交。角色决定契约形状，档位决定能力等级，车道决定如何到达供应商，姿态决定主代理会不会亲手改交付物。插件技能正文不写型号排名与拨盘取值，这些只写在用户路由档案里。

角色

角色权限返回
explorer只读证据：file:line、符号、原文
worker在契约的 Files 内可写diff 与验证证据
advisor只读不超过 300 词的 verdict。两种请求形状：决策（动工前）与验收（完工后：契约 + diff + receipt）

角色不含模型型号。卡住任务的接管是 worker 加一份接管契约，不是另一个角色。

档位与首轮准入

档位是 mainstay（主力）、crux（攻坚）、rescue（后援），与角色正交。任一角色可派任一档位。档位按型号划分，强度只在档内细分。设计意图是多数任务在 mainstay 结束，极少到 rescue。

mainstay主力新工作默认从这里开始，承担大多数日常工作。
crux攻坚已识别关键难点，或要处理相互制约的条件时，首轮可以直接用这一档。不设使用比例。
rescue后援只经 crux 的一次能力失败或用户声明进入，不作首轮选择。

拨盘是档位在车道内的实现：型号加强度。记法见第 2 节。格内取值写在用户路由档案，见第 12 节。

车道

车道决定怎么到达供应商。handoff lane 是条件成员：只有用户按任务或按会话声明之后，才进入第二段的候选。

grok laneGrok 家族Claude Code：plugin/scripts/run-grok.mjs，默认不传 model，跟随 CLI 默认型号。Cursor：钉 Grok 型号名的 Task。
codex laneGPT 家族两侧都跑 plugin/scripts/run-codex.mjs，白名单为 gpt-6-astra、gpt-6-luna、gpt-6.1-sol。Cursor 经 Shell，没有 receipt gate。
claude laneClaude 子代理仓内九份 agent 文件，无外部 CLI。按次 model 只接受别名。同模派发是它的一个拨盘：模型钉为会话模型。Cursor：generalPurpose 省略 model（inherit）。Claude Code：worker-* 的按次 model 设为会话模型。
handoff lane用户中介写入 .fable-advisor/handoff/<slug>.md。无 receipt，不在 receipt gate 视野内。验收对象是 diff，由架构师亲自重跑验证。

cursor lane 只在 Cursor 宿主存在，见第 8 节。它不进技能正文的车道表。

姿态

编排姿态主代理不亲手改交付物：写交付契约、派 worker、验收。这一姿态下的职责名是架构师。没人声明时，存在上游任务件（issue、spec、task）即为此姿态。
实现姿态主代理可亲手改交付物，同时仍可派任一角色。没人声明且没有上游任务件时为此姿态。

选择器顺序：用户声明或上层指示优先；二者都没有时，看有没有上游任务件。姿态相对一次派发成立：车道对自己的契约是实现姿态，对它再派的子代理可以是编排姿态。深度不限。Claude Code 把子代理嵌套上限定在主会话之下三层。

编排姿态下，交付物只经 worker 改，与改动大小无关。协调件（任务件、ADR、词表、工作流状态、发布版本字段）在任一姿态下主代理都可直接写。本仓的路径映射写在 AGENTS.md。类别不明时按交付物处理。

02两段式路由：首轮准入、格内选择与换候选

主代理持有需求、分解、契约、路由与验收。一次派发先选（角色, 档位），再在路由档案的该格里选一个候选。

第一段：（角色, 档位）

角色按产物选：证据走 explorer，改动走 worker，承诺或验收走 advisor。档位按首轮准入选：新工作从 mainstay 开始；已识别关键难点，或要处理相互制约的条件时，首轮可以直接用 crux；首轮 rescue 只凭用户声明。

第二段：格内选择

情况取哪个候选
没有声明，也没有合适的擅长点格内第一个候选，取它的 * 拨盘
任务落在档案为某个候选声明的擅长点上取那个候选。价格低也算擅长点
几个候选同样合适按档案声明的车道默认顺序

格内顺序是用户写定的偏好，不是能力排名，也不是价格排名。主代理不得按能力、价格或车道顺序重排格子。

换候选

候选不可用或超时时，契约原样交给同一格的另一个候选，并披露。三种情况都按档案声明的车道默认顺序换：整条车道不可用、单个候选不可用、codex runner 对某个型号启动失败。换候选不算能力失败。两条 CLI 车道都不可用时转 claude lane，并说明失去的跨厂商复核。可用性由这次派发的结果决定，不靠事先探测。

记法 model[a*, b, c]

拨盘写作 model[a*, b, c]：方括号里是这一格、这一型号可选的强度，都可直接选用，* 标默认；没有 * 的格以第一个列出的强度为默认。没有强度维度的型号裸写（例如 haiku-4-5）。已退役的 |（仅升级）记法不再使用。

车道默认顺序的具体值、Claude Code 中 explorer 的例外、擅长点示例都写在路由档案，见第 12 节。本节只说明机制。

03升级梯 R1–R4 与下一档

规则含义
R1验收未过：开返工票，同会话、同拨盘。契约缺口：给修正后的契约，仍回同一条车道会话。
R2返工票也未过，且诊断归为能力：记一次能力失败，进入下一档（mainstay → crux → rescue → 用户）。新会话，接管契约 = 原契约 + 上轮报告 + receipt。在下一档里按任务特点选型号。下限：新型号在档案排名中不低于失败的型号，没有别的候选时除外。同一型号必须提高强度。不同型号之间不比较强度名。
R3同一型号只提升一次，按完整模型标识计数。
R4执行时出现较大问题（工具反复失败、跑飞、触碰保留项）可跳过返工票，记一次能力失败，进入下一档。

环境问题和契约缺口不算失败。首轮就在 crux 的任务，在 crux 失败一次即进 rescue。rescue 失败交给用户，没有第四档。同一档内换型号不是能力失败后的下一步。

排名的读法由档案声明：每个家族只给自己的型号定位，定位从低到高为 starter、midrange、premium、flagship。不同家族的型号只按定位比较，同一定位内不分高下，所以在同一定位内跨厂商换模型不算降级。R2 的下限按定位判断：例如 worker 在 crux 用 flagship 的型号失败后，不能升到 rescue 里 premium 的型号。

提升跑在接管契约下，那是契约形状，不是档位。决策类型门的「同一问题两次失败」照旧触发 advisor 的决策形状，但 verdict 不再裁定升档。

04决策类型门、验证三层与批次验收

决策类型门约束任何主代理、任一档位、两种姿态。它是技能正文规则，不是 hook。到点位时咨询 advisor 的决策形状：传入决定、约束、备选；advisor 自己读代码。主代理对 verdict 采取行动，或公开分歧；不得静默忽略。没有机械强制，也没有逐 diff 过审。

  • 承诺一种架构、数据迁移、API 形状或重构策略
  • 推翻既定方案
  • 改公共接口或跨模块依赖
  • 放宽验收标准
  • 同一问题两次失败

advisor 的验收形状由验证第 3 层到达，不按步数触发。

报告是声称，不是证据。审查对象是契约。验收一张契约只关闭这张契约，不关闭整个任务。三层：

层级何时做什么
第 1 层每条车道默认接受车道的验证证据（命令、退出码、输出尾、对照工作树抽查）加上 git diff --stat。完整无范围的 git diff 不进主代理上下文。车道自己做的评审或验收是声称；复用它的命令输出，不重跑，把验收的力气花在车道看不到的部分：其他契约、车道不具备的环境、批次检查。
第 2 层报告、git diff --stat 或验证输出引起具体怀疑读限定路径的 git diff <file>。车道自己写的验收测试是声称的一部分，要读它。
第 3 层正确性关键、同族 diff、或用户要求评审advisor 以验收形状读 diff 与 receipt，返回 verdict 与标出的片段。同族 diff 优先换跨厂商候选。verdict 仍是声称，终裁在主代理。

每项检查只跑一次

  • 一份契约的检查列表只有一个执行者，由车道文档写明是谁。执行者跑过之后，不为收尾再跑一次。
  • 比单张契约改动更宽的昂贵检查是批次检查：全量测试、浏览器或端到端套件、完整构建或打包。它在批次最后一张契约落地之后跑一次，这就是批次验收。
  • 批次检查只有两种例外：后续工作依赖只有它能验证的结果时，提前跑；它发现的失败返工之后，再跑一次。
  • 一个批次容纳的契约数，以一次失败仍能归因为限。批次检查失败时，先追溯到致因契约，再给它开返工票。
  • 批次检查在任务件里登记一次，记为通过、失败或待跑，并附输出。有失败或待跑的批次检查（包括因提前停止而没跑的），任务就不算完成，除非用户豁免。
  • 主代理可以把批次的执行交给车道，判断仍归主代理。
  • 证据在其依据的代码、输入与环境未变时继续有效。换角色或换会话本身不是重跑理由。

「应该能工作」「测试应该过」，或者背后没有命令输出的验收，都不算完成。

05五部交付契约与两份前言

车道不共享主代理的上下文。每次派发携带五部：

部键内容
1. Objectiveobjective结果与验收标准，不是步骤
2. Filesfiles授权范围（路径或目录）；范围内新建文件允许
3. Interfacesinterfaces结果必须匹配的共享或外部契约；可以为无
4. Constraintsconstraints保留项：不得改什么、上游已钉死的选择、调用方留在自己会话里的操作。约束车道、它的子代理与它的验证命令
5. Verificationverificationworker：范围限于这张契约的改动及其调用方的检查。至少一条在 Objective 点名的行为未达成时会失败，这一条永不延后；先用能做到这一点的最便宜检查（现有测试，文本类改动用 grep），之后才写新的测试代码。批次检查不放进来，票据列出的也不放。explorer / advisor：期望的证据或 verdict 形状，可为空

Constraints 未钉死的实现选择归车道：不上报、不等待。契约缺口（预期行为不明、要求冲突、必须改保留接口、无法判定什么算通过）要上报，由架构师修正契约。

存在上游任务件时，契约引用它的路径，只内联验收标准、保留约束与本契约自己的检查，并标明哪些节有约束力。主代理不重述、不重规划。本仓把批次检查在功能 spec 或收尾票的 ## Batch checks 小节登记一次，跑过之后在同一处记录结果。

返工票是给同一车道的新契约，复用它的会话：Objective 写缺陷（违反的要求、可复现失败、期望行为、证据）；Files 仍是原范围；Verification 是能覆盖失败用例与修复波及范围的最小可运行检查，不是整个套件。票内不写修复方案。

共用文件或同一区域的多张票交给一个 worker，作为一张契约派发，每张票各有一条判定检查和一行报告。三种情况分开派发：超出一条车道的上下文；一张票需要另一张已核验的结果；一张票需要单独授权。这张契约验收一次，不逐票验收；提交只在授权或回滚边界处拆分。

两份前言

前言是执行侧契约的单源，与 runner 同目录解析：<plugin-root>/skills/orchestration/。当前 mode 所需的前言缺失时，runner 退出非零、不拉起子进程，stderr 指名文件，不写 receipt。

文件用于执行侧约定
lane-preamble.mdmode: implement（缺省）；claude lane 的 worker-*执行者持有 Files 内的交付物，可以自己拆分工作、派子代理。对自己 diff 的评审（自己做或子代理做）是自查；车道判定为高风险的契约，可以做一次独立验收；评审的发现用最窄的检查复核，连同证据写进报告，验收留给调用方。保留操作仍约束它及其子代理。Verification 条：检查列表只有一个执行者；契约写明 runner 会在车道退出后跑这份列表时，车道不为收尾再跑；没写时列表归车道，在结尾跑一次。工作中只跑能回答当前问题的最窄检查，例如一个测试文件；比改动更宽的昂贵检查（全量测试、浏览器或端到端套件、完整构建或打包、耗时长的整项目类型检查）属于调用方的批次，除非检查列表写了它，子代理也不跑。以 WORKER REPORT（OBJECTIVE / CHANGES / VERIFIED / GAPS）结尾，附实际跑过的检查的输出。
lane-preamble-report.mdmode: report；claude lane 的 explorer-*只读的 explorer 或 advisor。Files 是读取范围，不是写权限。回答 Objective。explorer 以证据形状结尾，advisor 以 verdict 形状结尾。不含 WORKER REPORT。

claude lane 与 Cursor 的 Task 都没有 runner 自动前置前言：派发 prompt 首行是读取所需前言的指令，按绝对路径给出，不是路径标签；worker 读 lane-preamble.md，explorer / advisor 读 lane-preamble-report.md。不要在契约正文里复述前言。advisor-* 自带完整正文。

06两条 runner：spec、receipt、错误类与报告模式

主代理把五部写成 JSON，放到目标仓的 .fable-advisor/pending/<slug>.json，然后跑 runner。车道在 runner 进程退出时结束。receipt 打印到 stdout，并写入 .fable-advisor/receipts/<spec_hash>.json。error_class: complete 时 runner 自己删除 pending spec。

node "<plugin-root>/scripts/run-codex.mjs" --spec .fable-advisor/pending/<slug>.json --cwd "$(pwd)"
node "<plugin-root>/scripts/run-grok.mjs" --spec .fable-advisor/pending/<slug>.json --cwd "$(pwd)"

未知顶层键或越界值记 spec_invalid，永不静默改写。CLI 车道的验收 = error_class: complete + 非空会话 id + 可对照工作树抽查的验证输出 + 技能正文的分层验收。引用 receipt 里的型号或强度时写「已提交，未观测」：那是 runner 提交给 CLI 的值，不是从运行事件读回来的。

spec 键

五部键：objective、files、interfaces、constraints、verification。implement 模式的 verification 至少一条；report 模式可以为空数组。files 在 report 模式是读取范围，也可以为空。

键codexgrok
modeimplement（缺省）或 report。其他值 → spec_invalid
model白名单恰为 gpt-6-astra（缺省）、gpt-6-luna、gpt-6.1-sol。名单外（包括 gpt-6-sol、gpt-5.6-luna、gpt-5.6-sol）→ spec_invalid，不拉起子进程默认省略：不传 -m，跟随 CLI 默认型号 grok-4.7。目录可读时按目录校验；目录不可读时跳过校验，由实跑决定可用性，不是 grok_unavailable

不换型号

两条 runner 都不换型号。codex runner 在会话建立前失败（preparation_stalled，或 codex_failed 且尚无会话 id）时只尝试一次：receipt 报告这个错误类，model_requested 与 model_used 都是请求的型号。主代理按第 2 节的换候选规则处理。不要预先探测 CLI 登录态；最多检查安装（which grok）。可用性以 receipt 为准。

检查列表的执行者

runner 是契约检查列表的唯一执行者。verification 非空时，runner 在 prompt 里告诉车道：runner 会在车道退出后自己跑这些命令，退出码与输出写进 receipt，非零退出仍算车道的失败；车道工作中按需跑检查，但不把这份列表当收尾步骤再跑。verification 为空时不注入这句话。runner 自己那次执行不变，它是车道无法伪造的证据。complete receipt 是那张契约的证据，不是对契约的验收，更不是对任务的验收。

检查失败时，从该检查的 output_log 读出失败用例，只重跑这些用例。为了查看失败而重跑整份列表，等于重复最贵的那一步。

receipt 字段

两条 runner 都写：receipt_version、mode、report（仅 report 模式带 CLI 最终消息，implement 为 null）、spec_hash、cwd、producer（codex 或 grok）、model、model_requested、model_used、fallback_reason、effort、resumed_from、end_to_close_ms、max_idle_ms、idle_timeout_sec、timeout_sec、started_at、finished_at、exit_status、error_class、dirty_baseline、changed_files、verification。

codex 另有 service_tier、codex_session_id、codex_final_message。grok 另有 grok_session_id（runner 注入 --session-id）、stop_reason、usage、total_cost_usd、grok_final_message。

fallback_reason 在两条 runner 上恒为 null。它只为兼容读 receipt 的调用方而保留。

verification 的每个条目有四个字段：command；exit_code；output_tail，即合并输出的最后 2,000 个字符；output_log，即完整输出日志相对于 --cwd 的路径 .fable-advisor/receipts/<spec_hash>.verification-<n>.log，n 从 1 开始，与命令在列表中的位置一致。日志是该命令的完整合并输出，边产生边写入；启动失败的错误信息也写进日志；同一 spec 再跑时覆盖旧日志。日志只记录，不改变被记录的命令：runner 不为日志暂停读取命令输出。写入队列超过 16 MiB 时，runner 放弃这份日志，并尽力删除不完整的文件；日志写不出时 output_log 为 null，stderr 打一行诊断，exit_code、output_tail 与 error_class 不受影响。没有跑检查的路径（idle_timeout、timeout、interrupted、preparation_stalled 等）的 verification 为空数组，不写日志。日志与 receipt 一样含命令输出，目标仓要把 .fable-advisor/ 加进 .gitignore。

dirty_baseline：拉起 CLI 之前跑一次 git status --porcelain。非空为 true，空为 false，这次 git status 本身失败为 null，运行继续。两条 runner、两种模式都记。

end_to_close_ms（终端事件到进程自然关闭；没看到终端事件或管道被强制释放时为 null）与 max_idle_ms 是诊断，不是门。

进程收尾

CLI 进程退出后，runner 停止执行计时，最多等两秒让继承的输出管道排空。之后释放剩余管道，记一条诊断，用观察到的退出状态继续验证与写 receipt。预检、git 检查与验证命令使用同一排空上限；这不限制仍在运行的验证命令。超时与中断先启动独立的两秒清理截止，再尝试杀进程树。Windows taskkill 有自己的两秒运行上限与两秒清理上限。诊断说没观察到退出时，先确认并停掉残留进程，再续跑或派另一个写入者。

运行中标记、心跳与等待

runner 读完合法 spec 后，以独占创建写运行中标记 .fable-advisor/running/<spec_hash>.json，内容为 runner、pid、spec 路径、开始时间、阶段（preparing | cli | verifying）与事件数。runner 每 60 秒刷新一次标记，同时向 stderr 写一行进度，例如 [run-grok] running 4m00s; phase cli; 132 events; last event 0m12s ago。stdout 仍只放 receipt。runner 在观察到的每条退出路径上删除标记；180 秒没刷新的标记属于已死的 runner。

同一 spec 已有新鲜标记时，第二个 runner 以状态 1 退出，不写 receipt，不启动 CLI，不动对方的标记：一份 spec 同一时间至多一个 runner。标记过期则接管。

Claude Code 的等待只有两条路径。第一条是前台运行 runner，适合预计远在 Bash timeout 之内完成的票。第二条是把 runner 本身作为后台 Bash 调用（run_in_background: true）运行，然后结束本轮或做互不依赖的工作，由宿主在进程退出时唤醒会话，再判断 receipt；可能超过 60 分钟的票走这一条。第二条只属于主会话：子代理结束本轮就是把报告交还上级，receipt gate 不在那次停止时运行，所以子代理在前台运行 runner。不要自写等待循环（sleep、while、until、pgrep 轮询），也不要把循环包进后台调用；反复读输出文件也不是等待。

运行中纠偏

CLI 车道运行中没有消息通道：runner 只交付一次提示词。要中途纠偏，用 kill <pid>（pid 取自运行中标记）向 runner 发 SIGTERM，让中断路径走完，写出 interrupted receipt。对 runner 的后台任务用 TaskStop 也会发 SIGTERM，但随后很快强制结束，可能截断 receipt。然后删除旧的 pending spec，排入修正后的契约，resume_session_id 设为那份 interrupted receipt 的会话 id，车道带着上下文继续。被中断的一轮没有验证结果，恢复后由 runner 重新验证。

错误类

共享：complete、spec_invalid、preparation_stalled、idle_timeout、timeout、interrupted、verification_failed、no_diff、unexpected_diff、empty_report、git_status_failed。

codex 另有 codex_unavailable（PATH 上没有 codex）、codex_failed。grok 另有 grok_unavailable（拉起进程得到 ENOENT）、grok_failed。

no_diff：implement 模式且 files 非空、运行后无改动；pending 文件留下。普通 spec 要调查；返工票上这可能表示缺陷无法复现。git_status_failed 只在 implement 模式出现，表示 runner 无法判定改了什么，不是 complete。idle_timeout 与 timeout 表示时钟切断，跳过验证；恢复路径是带该 receipt 会话 id 的返工票（resume_session_id），不是主代理手验工作树。

implement 模式应先有干净工作树：git status --porcelain 为空。开跑前已有脏文件时，空跑会看起来像做了工作。

报告模式语义

  • CLI 以只读工具集运行。codex 为 --sandbox read-only。
  • 前言用报告前言，不用 worker 前言。
  • 工作树没有被本车道弄脏，是正常结果，记 complete。receipt 另带 mode 与 report。
  • 开跑前干净、跑完变脏：unexpected_diff，不是 complete。
  • dirty_baseline: true 时不判 unexpected_diff。changed_files 仍记录运行后观察到的路径。此时只读工具集是唯一防线。
  • 运行后的 git status 失败不判 git_status_failed（ADR 0019）。changed_files 记空数组，dirty_baseline 保持开跑前的记录（开跑前也失败则为 null），然后照常判 empty_report 与 complete。所以没有 git 仓库的目录也能完成报告。
  • 收集到的报告文本为空或只有空白：empty_report，pending spec 留下。git 不可用时同样适用。
  • 判定顺序：先 unexpected_diff（本车道弄脏的树），再 empty_report，再 complete。git_status_failed 不在这个顺序里。
  • receipt gate 对报告模式的 pending spec 同样生效。

08Cursor：钉派发、cursor lane、runner 经 Shell、用户级门禁

钉模型的 Task

  • worker：generalPurpose + 显式 model，prompt 首行是读取 lane-preamble.md 的指令。
  • explorer：explore（或 generalPurpose）+ 显式 model，prompt 首行是读取 lane-preamble-report.md 的指令。

10receipt gate

插件 Stop hook，针对主会话自己：排了 spec 却不跑，或把非 complete 的 receipt 当完成。实现是 plugin/hooks/hooks.json 调 plugin/hooks/receipt-gate.py。

  • 扫描 <cwd>/.fable-advisor/pending/*.json。按 spec 文件 sha256 找 .fable-advisor/receipts/<digest>.json。
  • 没有 receipt，或 error_class 不是 complete，并且没有新鲜的运行中标记：stderr 列出 pending 文件，退出 2，拦住结束。拦截消息指引以后台 Bash 调用运行 runner，然后结束本轮。
  • 有新鲜运行中标记（.fable-advisor/running/<digest>.json，180 秒内刷新过）的 pending spec 不计入未匹配：车道在跑，放行结束，宿主在后台 runner 退出时唤醒会话。标记只覆盖它自己的 spec。
  • 没有 pending 目录：放行。
  • stop_hook_active 为真：放行，避免重入。
  • stdin 不是合法 JSON：失败时放行（退出 0）。没有 python 运行时：hook 包装同样失败时放行，并在 stderr 说明。

门禁分不清「结束本轮等待唤醒」与「runner 跑完前声称完成」；后者由等待规则与验收约束，runner 退出后的下一次结束照常检查。门禁只强制 receipt 存在且为 complete；内容仍由主代理判断。放弃或改道时要亲手删 pending 文件并说明，不能只靠这扇门。handoff 目录在 .fable-advisor/handoff/，故意不在此视野内。Cursor 经 Shell 的 runner 按没有这扇门设计。

  • 格内第一个候选是默认。没有声明，也没有合适的擅长点时，取它的 * 拨盘，不取最便宜的候选。

14检查范围、批次检查与完整输出（ADR 0029）

6.0.0 的最后一个已推送提交是 7c458e4（2026-09-29）。本节的改动来自两次编排会话里的重复检查：cc-usage 的一次会话跑了 96 次检查，约 4.7 小时；rustpad 的一次会话跑了 138 次。调查结论是多方成因叠加：插件让契约默认带全量回归，返工票带整份列表，2,000 字符的输出尾部迫使主代理为查看失败而重跑；项目记忆要求验证命令一律写全量测试；codex 车道经宿主全局规则在车道内另做验收。证据、计数口径与各方成因在 .scratch/verification-defaults/problem-report.md。

契约第 5 部只放本契约范围内的检查

改了什么worker 契约的 Verification 只放范围限于本契约改动及其调用方的检查：至少一条在 Objective 点名的行为未达成时会失败，永不延后；先用能做到这一点的最便宜检查（现有测试，文本类改动用 grep），之后才写新的测试代码。批次检查不进契约，票据列出的也不进。存在上游任务件时，契约内联「本契约自己的检查」，不再内联「验证命令」。

为什么「判定本契约的检查」与「内联验证命令」两条，让票据或记忆里的全量命令原样进入每份契约。cc-usage 的 7 份 CLI 契约都带全量测试，runner 因此跑了 7 次全量测试。

依据ADR 0029 决策 1，修订 ADR 0020 决策 2；任务件 .scratch/verification-defaults/spec.md。

昂贵的宽检查归批次，并有预算

改了什么全量测试、浏览器或端到端套件、完整构建或打包是批次检查，在批次最后一张契约落地后跑一次。例外只有两种：后续工作依赖只有它能验证的结果时提前跑；它发现的失败返工之后再跑。批次大小以一次失败仍能归因为限。结果在任务件里登记为通过、失败或待跑并附输出；有失败或待跑的批次检查，包括因提前停止而没跑的，任务不算完成，除非用户豁免。「共用昂贵准备」这一触发词退役。CONTEXT.md 的「批次验收」词条随之改写；本仓的 docs/agents/issue-tracker.md 把逐票的 ## Held for batch acceptance 改为在 spec 或收尾票的 ## Batch checks 下登记一次。

为什么全量测试是昂贵的检查，不是准备工作，旧触发词对不上它；暂缓一项检查还要在契约和任务件里各登记一次，比不暂缓更费事。用户的要求是「能一起验的就集中一起验（不强求只在最后验一次，防止范围太大验不过来）」。

依据ADR 0029 决策 2、9，修订 ADR 0020 决策 3、8。

同一区域的票并入一份契约，按契约验收

改了什么共用文件或同一区域的多张票交给一个 worker，作为一张契约派发，每张票各有一条判定检查和一行报告。超出一条车道的上下文、一张票需要另一张已核验的结果、一张票需要单独授权时，分开派发。合并后的契约验收一次；提交只在授权或回滚边界处拆分。

为什么cc-usage 的 06 至 09 四张票合成了一份契约，但仍逐票验收、逐票提交，16 次检查都是逐票往返的收尾检查。只合并契约、不合并验收，往返次数不变。

返工只验最小的检查

运行中标记与心跳

为什么runner 运行期间原本没有任何输出，主会话和用户都看不出车道是否还活着。Windows 上 Python 的 os.kill(pid, 0) 会终止目标进程，pid 还会被复用。

17升级步骤与注意点

从 6.0.0 升级到 6.1.0 没有不兼容改动。下面三处要留意，升级步骤在本节末尾。

codex 型号名手写的 spec 或脚本里用到 gpt-6-sol 时，改为 gpt-6.1-sol；旧名判 spec_invalid，不拉起子进程。

receipt 新字段verification 的条目多了 output_log。按固定键集合严格解析 receipt 的调用方要接受这个键。

目标仓的忽略规则runner 运行时会在目标仓写 .fable-advisor/running/ 与输出日志。目标仓应已把 .fable-advisor/ 加进 .gitignore，否则它们会出现在 git status 里。

升级后要做什么
  1. 两侧都跑插件更新：claude plugin marketplace update fable-advisor，然后 claude plugin update fable-advisor@fable-advisor。Windows 侧从 WSL 执行：cd /mnt/c && cmd.exe /c "claude plugin marketplace update fable-advisor && claude plugin update fable-advisor@fable-advisor"。
  2. 确认两侧缓存都出现 6.1.0，并抽查新内容已落地：缓存里的 skills/orchestration/SKILL.md 含 is a batch check，scripts/run-codex.mjs 含 output_log。
  3. 从本仓检出跑伴生安装器：python3 scripts/install-user-level.py --home ~ --home /mnt/c/Users/Shy，再加 --check 确认没有漂移。
  4. 重启两侧正在运行的 Claude Code 与 Cursor 会话。插件缓存与 agent 文件只在新会话生效。
  5. 在新会话里以后台 Bash 调用运行一次 runner 并结束本轮，确认 receipt gate 放行、runner 退出后会话被唤醒。
