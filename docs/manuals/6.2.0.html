01

本版完整行为

01角色 × 档位 × 车道 × 姿态

这四个维度互相正交。角色决定契约形状，档位决定能力等级，车道决定如何到达供应商，姿态决定主代理会不会亲手改交付物。插件技能正文不写型号排名与拨盘取值，这些只写在用户路由档案里。

角色

角色权限返回
explorer只读证据：file:line、符号、原文
worker在契约的 Files 内可写diff 与验证证据
advisor只读不超过 300 词的 verdict。两种请求形状：决策（动工前）与验收（完工后：契约 + diff + receipt）

角色不含模型型号。卡住任务的接管是 worker 加一份接管契约，不是另一个角色。

档位与首轮准入

档位是 mainstay（主力）、crux（攻坚）、rescue（后援），与角色正交。任一角色可派任一档位。档位是每个角色的一组拨盘：按角色、型号、强度划分，同一型号可以按强度分在不同档位。设计意图是多数任务在 mainstay 结束，极少到 rescue。

mainstay主力新工作默认从这里开始，承担大多数日常工作。
crux攻坚已识别关键难点，或要处理相互制约的条件时，首轮可以直接用这一档。不设使用比例。
rescue后援只经 crux 的一次能力失败或用户声明进入，不作首轮选择。

拨盘是档位在车道内的实现：型号加强度。记法见第 2 节。格内取值写在用户路由档案，见第 12 节。

车道

车道决定怎么到达供应商。handoff lane 是条件成员：只有用户按任务或按会话声明之后，才进入第二段的候选。

grok laneGrok 家族Claude Code：plugin/scripts/run-grok.mjs，spec 必须显式写 model 与 effort。Cursor：钉 Grok 型号名的 Task。
codex laneGPT 家族两侧都跑 plugin/scripts/run-codex.mjs，白名单为 gpt-6-astra、gpt-6-luna、gpt-6.1-sol。Cursor 经 Shell，没有 receipt gate。
claude laneClaude 子代理仓内九份 agent 文件，无外部 CLI。按次 model 只接受别名。同模派发是它的一个拨盘：模型钉为会话模型，只限 worker，路由写 tier=same-model（第 14 节）。Cursor：generalPurpose 省略 model（inherit）。Claude Code：worker-* 的按次 model 设为会话模型。
handoff lane用户中介写入 .fable-advisor/handoff/<slug>.md。无 receipt，不在 receipt gate 视野内。验收对象是 diff，由架构师亲自重跑验证。

cursor lane 只在 Cursor 宿主存在，见第 8 节。它不进技能正文的车道表。

姿态

编排姿态主代理不亲手改交付物：写交付契约、派 worker、验收。这一姿态下的职责名是架构师。没人声明时，存在上游任务件（issue、spec、task）即为此姿态。
实现姿态主代理可亲手改交付物，同时仍可派任一角色。没人声明且没有上游任务件时为此姿态。

选择器顺序：用户声明或上层指示优先；二者都没有时，看有没有上游任务件。姿态相对一次派发成立：车道对自己的契约是实现姿态，对它再派的子代理可以是编排姿态。深度不限。Claude Code 把子代理嵌套上限定在主会话之下三层。

编排姿态下，交付物只经 worker 改，与改动大小无关。协调件（任务件、ADR、词表、工作流状态、发布版本字段）在任一姿态下主代理都可直接写。本仓的路径映射写在 AGENTS.md。类别不明时按交付物处理。

02两段式路由：档位准入、路由、格内选择与换候选

主代理持有需求、分解、契约、路由与验收。一次派发先选（角色, 档位），再在路由档案的该格里选一个候选。

第一段：（角色, 档位）与档位准入

角色按产物选：证据走 explorer，改动走 worker，承诺或验收走 advisor。档位先按任务难点或升级梯定：新工作从 mainstay 开始；已识别关键难点，或要处理相互制约的条件时，首轮可以直接用 crux，不设使用比例；首轮 rescue 只凭用户声明；升档按升级梯。

椰椰声明的家族或型号只筛选候选，不设档位。主代理取满足三个条件的最低一档：

  • 不低于按难点或升级梯定下的档位；
  • 这一档的格里有符合声明的候选；
  • 这次派发有该档接受的依据（mainstay 不需要依据）。

家族或型号声明可以作为 crux 的 user-declaration 依据，ref 写椰椰的原话。它不算 rescue 的准入。三个条件同时满足不了时，主代理向椰椰报告冲突，不自动降档。

路由：每次派发写明去向

每次派发写明路由：角色、档位、拨盘，高于 mainstay 时再加依据。经 SendMessage 或 resume 发给已有会话的消息也写路由。依据种类按角色和档位定：

角色cruxrescue
worker、explorerkey-difficulty、failure、user-declarationfailure、user-declaration
advisorlow-confidence、user-declarationuser-declaration

依据带非空的 ref：key-difficulty 写难点；failure 写失败那次派发的标识（回执哈希、会话 id 或 agentId）；low-confidence 写那条低置信度的 verdict；user-declaration 写椰椰的原话。同模派发有自己的路由：只限 worker，档位写 same-model，依据种类也是 same-model，ref 写产物类别。

路由由程序机械校验：runner 在启动 CLI 之前校验 spec（第 6 节），Claude Code 里由 route gate 校验 Agent 与 SendMessage（第 14 节）。校验只查依据存在、格式合规，不查它是否属实；属实与否仍由主代理判断。

第二段：格内选择

情况取哪个候选
没有声明，也没有合适的擅长点格内第一个候选，取它的 * 拨盘
任务落在档案为某个候选声明的擅长点上取那个候选。价格低也算擅长点
几个候选同样合适按档案声明的车道默认顺序

格内顺序是用户写定的偏好，不是能力排名，也不是价格排名。主代理不得按能力、价格或车道顺序重排格子。

换候选

候选不可用或超时时，契约原样交给同一格的另一个候选，并披露。三种情况都按档案声明的车道默认顺序换：整条车道不可用、单个候选不可用、codex runner 对某个型号启动失败。换候选不算能力失败。两条 CLI 车道都不可用时转 claude lane，并说明失去的跨厂商复核。可用性由这次派发的结果决定，不靠事先探测。

记法 model[a*, b, c]

拨盘写作 model[a*, b, c]：方括号里是这一格、这一型号可选的强度，都可直接选用，* 标默认；没有 * 的格以第一个列出的强度为默认。没有强度维度的型号裸写（例如 haiku-4-5）。已退役的 |（仅升级）记法不再使用。

车道默认顺序的具体值、Claude Code 中 explorer 的例外、擅长点示例都写在路由档案，见第 12 节。本节只说明机制。

03升级梯 R1–R4 与下一档

规则含义
R1验收未过：开返工票，同拨盘，在续用窗口之内用同一会话。契约缺口：给修正后的契约，条件相同。超出窗口时，在同一档位、同一拨盘上新开会话（第 15 节）。
R2返工票也未过，且诊断归为能力：记一次能力失败，进入下一档（mainstay → crux → rescue → 用户）。新会话，接管契约 = 原契约 + 上轮报告 + receipt。在下一档里按任务特点选型号。下限：新型号在档案排名中不低于失败的型号，没有别的候选时除外。同一型号必须提高强度。不同型号之间不比较强度名。
R3同一型号只提升一次，按完整模型标识计数。
R4执行时出现较大问题（工具反复失败、跑飞、触碰保留项）可跳过返工票，记一次能力失败，进入下一档。

环境问题和契约缺口不算失败。首轮就在 crux 的任务，在 crux 失败一次即进 rescue。rescue 失败交给用户，没有第四档。同一档内换型号不是能力失败后的下一步。

排名的读法由档案声明：每个家族只给自己的型号定位，定位从低到高为 starter、midrange、premium、flagship。不同家族的型号只按定位比较，同一定位内不分高下，所以在同一定位内跨厂商换模型不算降级。R2 的下限按定位判断：例如 worker 在 crux 用 flagship 的型号失败后，不能升到 rescue 里 premium 的型号。

提升跑在接管契约下，那是契约形状，不是档位。决策类型门的「同一问题两次失败」照旧触发 advisor 的决策形状，但 verdict 不再裁定升档。

窗口之外新开会话不是升档，失败计数不变，强度也不改。续用只在窗口之内进行，见第 15 节。

04全局规划、决策类型门、验证三层与批次验收

决策类型门约束任何主代理、任一档位、两种姿态。它是技能正文规则，不是 hook。到点位时咨询 advisor 的决策形状：传入决定、约束、备选；advisor 自己读代码。主代理对 verdict 采取行动，或公开分歧；不得静默忽略。没有机械强制，也没有逐 diff 过审。

  • 承诺一种架构、数据迁移、API 形状或重构策略
  • 推翻既定方案
  • 改公共接口或跨模块依赖
  • 放宽验收标准
  • 同一问题两次失败

advisor 的验收形状由验证第 3 层到达，不按步数触发。

派发前的全局规划

任务有两张以上的票时，主代理在第一次派发前把计划写进任务件。计划有四项：

  • 依赖：哪张票需要另一张票的结果（例如接口），或在同一文件上先后修改。
  • 契约：共用文件或同一区域的票并成一份契约，每张票各有一条判定检查和一行报告；超出一条车道的上下文、一张票需要另一张已核验的结果、或一张票需要单独授权时，分开派发。契约验收一次，不逐票验收。
  • 隔离：每份契约的 Files。同时进行的契约若会共用一个工作目录，就各用一个独立的工作目录（git worktree）；只换分支名而共用一个工作目录，不算隔离。Cursor 里普通的 Task 共用工作区，并发契约改用隔离工作树的派发类型（best-of-n-runner，一次尝试），或者依次执行。
  • 宽检查：每项宽检查覆盖哪些契约，由谁跑，在哪个时点跑。

只等真实的依赖。 没有全局的阶段屏障。没有依赖的契约在一条消息里同时派发；顺序链和单文件手术保持串行。一份契约在它需要的契约验收通过、判定检查就绪后就派发，不等无关的契约。只有它需要的结果只能由某项宽检查证明时，才等这项宽检查。一份独立契约的验收、返工和检查，不挡另一份契约的派发。

提交只在授权或回滚边界处拆分，与验收分开。向椰椰问提交粒度时，选项里包含按契约提交。高风险工作可以让两个候选竞赛同一份契约，取较强的 diff；每个候选各用一个独立的工作目录和执行记录。

报告是声称，不是证据。审查对象是契约。验收一张契约只关闭这张契约，不关闭整个任务。三层：

层级何时做什么
第 1 层每条车道默认对照契约逐条核对三样东西：报告对每条验收标准的说法；车道的检查证据（命令、退出码、输出尾，对照工作树抽查）；承载 Objective 所述行为的文件，按路径限定的 git diff <file>（文件清单从 git diff --stat 得到）。测试只证明它覆盖的断言：差异实现的是别的行为时，即使检查全部通过也拒收。差异太大时交 advisor 阅读；主代理核对标准、证据、结论是否一一对应，再读 advisor 标出的片段。完整无范围的 git diff 不进主代理上下文。车道自己做的评审或验收是声称；复用它的命令输出，不重跑，把验收的力气花在车道看不到的部分：其他契约、车道不具备的环境、批次检查。
第 2 层报告、git diff --stat 或验证输出引起具体怀疑读它指向的其他文件的限定路径 git diff <file>。车道自己写的验收测试是声称的一部分，要读它。
第 3 层正确性关键、同族 diff、或用户要求评审advisor 以验收形状读 diff 与 receipt，返回 verdict 与标出的片段。同族 diff 优先换跨厂商候选。verdict 仍是声称，终裁在主代理。

每项检查只跑一次

  • 一份契约的检查列表只有一个执行者，由车道文档写明是谁。执行者跑过之后，不为收尾再跑一次。契约只放本契约的判定检查。
  • 宽检查归批次：全量测试、渲染或浏览器检查、端到端套件、完整构建或打包、与其他契约的检查共用昂贵准备（服务、浏览器、设备、构建）的检查，以及主代理自己做的渲染和人工检查。
  • 每项宽检查在它覆盖的契约都落地并验收之后跑一次，这就是批次验收。它只挡需要它结果的工作，不挡其余契约的派发。只在它发现的失败返工之后再跑。
  • 一个批次容纳的契约数，以一次失败仍能归因为限。批次检查失败时，先追溯到致因契约，再给它开返工票；归因不到一份契约时，把批次分小。
  • 批次检查在任务件里登记一次，记为通过、失败或待跑，并附输出。有失败或待跑的批次检查（包括因提前停止而没跑的），任务就不算完成，除非用户豁免。
  • 主代理可以把批次的执行交给车道，判断仍归主代理。
  • 证据在其依据的代码、输入与环境未变时继续有效。换角色或换会话本身不是重跑理由。

「应该能工作」「测试应该过」，或者背后没有命令输出的验收，都不算完成。

05五部交付契约与两份前言

车道不共享主代理的上下文。每次派发携带五部：

部键内容
1. Objectiveobjective结果与验收标准，不是步骤
2. Filesfiles授权范围（路径或目录）；范围内新建文件允许
3. Interfacesinterfaces结果必须匹配的共享或外部契约；可以为无
4. Constraintsconstraints保留项：不得改什么、上游已钉死的选择、调用方留在自己会话里的操作。约束车道、它的子代理与它的验证命令
5. Verificationverificationworker：范围限于这张契约的改动及其调用方的检查。至少一条在 Objective 点名的行为未达成时会失败，这一条永不延后；先用能做到这一点的最便宜检查（现有测试，文本类改动用 grep），之后才写新的测试代码。批次检查不放进来，票据列出的也不放。explorer / advisor：期望的证据或 verdict 形状，可为空

Constraints 未钉死的实现选择归车道：不上报、不等待。契约缺口（预期行为不明、要求冲突、必须改保留接口、无法判定什么算通过）要上报，由架构师修正契约。

存在上游任务件时，契约引用它的路径，只内联验收标准、保留约束与本契约自己的检查，并标明哪些节有约束力。主代理不重述、不重规划。本仓把批次检查在功能 spec 或收尾票的 ## Batch checks 小节登记一次，跑过之后在同一处记录结果。

返工票是给同一车道的新契约，在续用窗口之内复用它的会话（第 15 节）：Objective 写缺陷（违反的要求、可复现失败、期望行为、证据）；Files 仍是原范围；Verification 是能覆盖失败用例与修复波及范围的最小可运行检查，不是整个套件。票内不写修复方案。

共用文件或同一区域的多张票交给一个 worker，作为一张契约派发，每张票各有一条判定检查和一行报告。三种情况分开派发：超出一条车道的上下文；一张票需要另一张已核验的结果；一张票需要单独授权。这张契约验收一次，不逐票验收；提交只在授权或回滚边界处拆分。

两份前言

路由校验

runner 在拉起 CLI 之前校验路由，并用 plugin/scripts/routing-profile.mjs 解析随插件发布的路由档案（<plugin-root>/skills/orchestration/routing-profile.md）。校验失败记 spec_invalid，不拉起子进程，stderr 打一行诊断。档案读不出或解析失败也是 spec_invalid。

  • 角色与模式匹配：implement 只收 worker，report 收 explorer 与 advisor。
  • 拨盘（model 加 effort）在档案里该角色、该档位的格里。runner 在两个宿主上都运行，所以取 Claude Code 表与 Cursor 表同一格的并集。
  • codex 按补齐省略默认值之后的有效拨盘校验。grok 必须显式写 model 和 effort，因为 runner 无从得知 CLI 自己的默认值。
  • 依据种类按角色和档位合规，ref 非空。
  • tier: same-model 被拒。

校验只查依据存在、格式合规，不查真假。

不换型号

两条 runner 都不换型号。codex runner 在会话建立前失败（preparation_stalled，或 codex_failed 且尚无会话 id）时只尝试一次：receipt 报告这个错误类，model_requested 与 model_used 都是请求的型号。主代理按第 2 节的换候选规则处理。不要预先探测 CLI 登录态；最多检查安装（which grok）。可用性以 receipt 为准。

检查列表的执行者

runner 是契约检查列表的唯一执行者。verification 非空时，runner 在 prompt 里告诉车道：runner 会在车道退出后自己跑这些命令，退出码与输出写进 receipt，非零退出仍算车道的失败；车道工作中按需跑检查，但不把这份列表当收尾步骤再跑。verification 为空时不注入这句话。runner 自己那次执行不变，它是车道无法伪造的证据。complete receipt 是那张契约的证据，不是对契约的验收，更不是对任务的验收。

检查失败时，从该检查的 output_log 读出失败用例，只重跑这些用例。为了查看失败而重跑整份列表，等于重复最贵的那一步。

receipt 字段

两条 runner 都写：receipt_version、mode、role、tier、basis、lane_finished_at、report（仅 report 模式带 CLI 最终消息，implement 为 null）、spec_hash、cwd、producer（codex 或 grok）、model、model_requested、model_used、fallback_reason、effort、resumed_from、end_to_close_ms、max_idle_ms、idle_timeout_sec、timeout_sec、started_at、finished_at、exit_status、error_class、dirty_baseline、changed_files、verification。

codex 另有 service_tier、codex_session_id、codex_final_message。grok 另有 grok_session_id（runner 注入 --session-id）、stop_reason、usage、total_cost_usd、grok_final_message。

fallback_reason 在两条 runner 上恒为 null。它只为兼容读 receipt 的调用方而保留。

lane_finished_at 是 CLI 进程退出的时刻，在 runner 跑验证之前记录；它是续用窗口的时间来源（第 15 节）。finished_at 在验证之后才记录，不用于窗口。spec_invalid 时 CLI 没有启动，lane_finished_at 为 null。role、tier、basis 记 spec 的 JSON 里写的值，缺键时为 null；spec 不是合法 JSON 时三者都是 null。读取 spec 时被拒（缺字段、值非法、未知键）和读完后路由校验未通过，都按此记录。

verification 的每个条目有四个字段：command；exit_code；output_tail，即合并输出的最后 2,000 个字符；output_log，即完整输出日志相对于 --cwd 的路径 .fable-advisor/receipts/<spec_hash>.verification-<n>.log，n 从 1 开始，与命令在列表中的位置一致。日志是该命令的完整合并输出，边产生边写入；启动失败的错误信息也写进日志；同一 spec 再跑时覆盖旧日志。日志只记录，不改变被记录的命令：runner 不为日志暂停读取命令输出。写入队列超过 16 MiB 时，runner 放弃这份日志，并尽力删除不完整的文件；日志写不出时 output_log 为 null，stderr 打一行诊断，exit_code、output_tail 与 error_class 不受影响。没有跑检查的路径（idle_timeout、timeout、interrupted、preparation_stalled 等）的 verification 为空数组，不写日志。日志与 receipt 一样含命令输出，目标仓要把 .fable-advisor/ 加进 .gitignore。

dirty_baseline：拉起 CLI 之前跑一次 git status --porcelain。非空为 true，空为 false，这次 git status 本身失败为 null，运行继续。两条 runner、两种模式都记。

end_to_close_ms（终端事件到进程自然关闭；没看到终端事件或管道被强制释放时为 null）与 max_idle_ms 是诊断，不是门。

进程收尾

CLI 进程退出后，runner 停止执行计时，最多等两秒让继承的输出管道排空。之后释放剩余管道，记一条诊断，用观察到的退出状态继续验证与写 receipt。预检、git 检查与验证命令使用同一排空上限；这不限制仍在运行的验证命令。超时与中断先启动独立的两秒清理截止，再尝试杀进程树。Windows taskkill 有自己的两秒运行上限与两秒清理上限。诊断说没观察到退出时，先确认并停掉残留进程，再续跑或派另一个写入者。

运行中标记、心跳与等待

runner 读完合法 spec 后，以独占创建写运行中标记 .fable-advisor/running/<spec_hash>.json，内容为 runner、pid、spec 路径、开始时间、阶段（preparing | cli | verifying）与事件数。runner 每 60 秒刷新一次标记，同时向 stderr 写一行进度，例如 [run-grok] running 4m00s; phase cli; 132 events; last event 0m12s ago。stdout 仍只放 receipt。runner 在观察到的每条退出路径上删除标记；180 秒没刷新的标记属于已死的 runner。

同一 spec 已有新鲜标记时，第二个 runner 以状态 1 退出，不写 receipt，不启动 CLI，不动对方的标记：一份 spec 同一时间至多一个 runner。标记过期则接管。

Claude Code 的等待只有两条路径。第一条是前台运行 runner，适合预计远在 Bash timeout 之内完成的票。第二条是把 runner 本身作为后台 Bash 调用（run_in_background: true）运行，然后结束本轮或做互不依赖的工作，由宿主在进程退出时唤醒会话，再判断 receipt；可能超过 60 分钟的票走这一条。第二条只属于主会话：子代理结束本轮就是把报告交还上级，receipt gate 不在那次停止时运行，所以子代理在前台运行 runner。不要自写等待循环（sleep、while、until、pgrep 轮询），也不要把循环包进后台调用；反复读输出文件也不是等待。

运行中纠偏

CLI 车道运行中没有消息通道：runner 只交付一次提示词。要中途纠偏，用 kill <pid>（pid 取自运行中标记）向 runner 发 SIGTERM，让中断路径走完，写出 interrupted receipt。对 runner 的后台任务用 TaskStop 也会发 SIGTERM，但随后很快强制结束，可能截断 receipt。然后删除旧的 pending spec，排入修正后的契约，resume_session_id 设为那份 interrupted receipt 的会话 id，车道带着上下文继续。这条续用同样只在续用窗口之内进行（第 15 节）。被中断的一轮没有验证结果，恢复后由 runner 重新验证。

错误类

共享：complete、spec_invalid、preparation_stalled、idle_timeout、timeout、interrupted、verification_failed、no_diff、unexpected_diff、empty_report、git_status_failed。

codex 另有 codex_unavailable（PATH 上没有 codex）、codex_failed。grok 另有 grok_unavailable（拉起进程得到 ENOENT）、grok_failed。

no_diff：implement 模式且 files 非空、运行后无改动；pending 文件留下。普通 spec 要调查；返工票上这可能表示缺陷无法复现。git_status_failed 只在 implement 模式出现，表示 runner 无法判定改了什么，不是 complete。idle_timeout 与 timeout 表示时钟切断，跳过验证；恢复路径是在续用窗口之内、带该 receipt 会话 id 的返工票（resume_session_id），不是主代理手验工作树；窗口之外则新开会话（第 15 节）。

implement 模式应先有干净工作树：git status --porcelain 为空。开跑前已有脏文件时，空跑会看起来像做了工作。

报告模式语义

  • CLI 以只读工具集运行。codex 为 --sandbox read-only。
  • 前言用报告前言，不用 worker 前言。
  • 工作树没有被本车道弄脏，是正常结果，记 complete。receipt 另带 mode 与 report。
  • 开跑前干净、跑完变脏：unexpected_diff，不是 complete。
  • dirty_baseline: true 时不判 unexpected_diff。changed_files 仍记录运行后观察到的路径。此时只读工具集是唯一防线。
  • 运行后的 git status 失败不判 git_status_failed（ADR 0019）。changed_files 记空数组，dirty_baseline 保持开跑前的记录（开跑前也失败则为 null），然后照常判 empty_report 与 complete。所以没有 git 仓库的目录也能完成报告。
  • 收集到的报告文本为空或只有空白：empty_report，pending spec 留下。git 不可用时同样适用。
  • 判定顺序：先 unexpected_diff（本车道弄脏的树），再 empty_report，再 complete。git_status_failed 不在这个顺序里。
  • receipt gate 对报告模式的 pending spec 同样生效。

08Cursor：钉派发、cursor lane、runner 经 Shell、用户级门禁

Cursor 经 Claude 插件兼容路径加载本插件。grok lane、claude lane 与 cursor lane 是原生 Task 派发，各自钉模型。codex lane 不在 Task 枚举里。

钉模型的 Task

  • worker：generalPurpose + 显式 model，prompt 第一行是路由行，第二行是读取 lane-preamble.md 的指令。
  • explorer：explore（或 generalPurpose）+ 显式 model，prompt 第一行是路由行，第二行是读取 lane-preamble-report.md 的指令。
  • advisor：具名 advisor-* agent，显式钉模型，prompt 第一行是路由行，第二行是读取报告前言的指令。

Cursor 里 Task 派发的路由只有文本规则：没有 hook 校验路由行，用户级的钉模型 hook 也不校验它。resume 的提示词同样以路由行开头。

钉的家族就是车道：Grok 家族是 grok lane，Claude 家族是 claude lane，Cursor 自家模型是 cursor lane。钉的型号名是一个拨盘，即该格档位内的一个型号加强度。插件 agent 的文首 model: 在 Cursor 不生效；省略 model 会继承会话模型。Cursor 不向主代理回传执行元数据，披露时标「已请求，未确认」。

强度钉在型号名上。档案里的 model[…] 在这里映射为型号名变体。当回合的允许名单只约束钉型号的 Task 派发：某个候选需要的变体不在名单里，就跳过这个候选，并在披露里说明。

同模派发是唯一允许省略 model 的派发：编排姿态下，服务本仓 AGENTS.md 点名的类别（plugin/skills/**——不含 routing-profile.md——与 plugin/agents/** 下的准则散文），generalPurpose 继承会话模型。披露里写 inherit，以免被当成漏钉。它的路由写 tier=same-model。

验收走技能正文的三层；Task 派发没有 receipt，也没有 runner，所以契约检查列表归车道，在结尾跑一次，报告里的输出就是全部证据。返工用 Task resume 加返工契约，且只在 1 小时的续用窗口之内。窗口从 Task 结果返回的时刻算起：主代理在结果到达时用 Shell（date -u +%Y-%m-%dT%H:%M:%SZ）把时刻记进任务件；没有记录就按窗口已过处理，新开会话（第 15 节）。再失败则按升级梯归因，能力失败进入下一档，用新派发加接管契约。竞赛用隔离工作树的派发类型（Task 枚举里的 best-of-n-runner）。并发契约若会共用工作区，同样用这个派发类型（一次尝试），否则依次执行；经 Shell 并发的 codex runner 各用一个 git worktree 作 --cwd。

codex runner 经 Shell

10receipt gate

插件 Stop hook，针对主会话自己：排了 spec 却不跑，或把非 complete 的 receipt 当完成。实现是 plugin/hooks/hooks.json 调 plugin/hooks/receipt-gate.py。

  • 扫描 <cwd>/.fable-advisor/pending/*.json。按 spec 文件 sha256 找 .fable-advisor/receipts/<digest>.json。
  • 没有 receipt，或 error_class 不是 complete，并且没有新鲜的运行中标记：stderr 列出 pending 文件，退出 2，拦住结束。拦截消息指引以后台 Bash 调用运行 runner，然后结束本轮。
  • 有新鲜运行中标记（.fable-advisor/running/<digest>.json，180 秒内刷新过）的 pending spec 不计入未匹配：车道在跑，放行结束，宿主在后台 runner 退出时唤醒会话。标记只覆盖它自己的 spec。
  • 没有 pending 目录：放行。
  • stop_hook_active 为真：放行，避免重入。
  • stdin 不是合法 JSON：失败时放行（退出 0）。没有 python 运行时：hook 包装同样失败时放行，并在 stderr 说明。

门禁分不清「结束本轮等待唤醒」与「runner 跑完前声称完成」；后者由等待规则与验收约束，runner 退出后的下一次结束照常检查。门禁只强制 receipt 存在且为 complete；内容仍由主代理判断。放弃或改道时要亲手删 pending 文件并说明，不能只靠这扇门。handoff 目录在 .fable-advisor/handoff/，故意不在此视野内。Cursor 经 Shell 的 runner 按没有这扇门设计。

plugin/hooks/hooks.json 现在登记两个 hook：Stop 的 receipt gate，和 PreToolUse 的 route gate（第 14 节）。两者在没有 python 运行时都放行。

12路由档案

填充表是（角色, 档位）→ 候选车道与拨盘的有序表，属于用户判断，随插件发布，但不是插件机制。技能直接读插件内的档案，不接受调用方点名的其他档案；首次分配模型前读；档案变化或滑出上下文时重读；读不到则报缺口，不假定内容。

角色路径
档案（唯一来源，随插件发布，技能直接读取）plugin/skills/orchestration/routing-profile.md
中文译本（镜像孪生，不发布）docs/zh/skills/orchestration/routing-profile.md

结构：声明日期与锚定型号 → 档位与格内选择 → 型号排名 → 已声明假设 → advisor 映射 → 会话续用窗口 → Claude Code 候选（到达方式、每个 claude 拨盘的 agent 文件与别名、表）→ Cursor 候选（按实际调用入口判断可用性、表）。表头形状是角色 ×（mainstay / crux / rescue）。口头声明与调整方法两节已从档案移出，规则并入 SKILL.md 与本仓 AGENTS.md。

格内选择规则的含义

  • 格内第一个候选是默认。没有声明，也没有合适的擅长点时，取它的 * 拨盘，不取最便宜的候选。
  • 格内顺序是用户写定的偏好。档案写明了一处刻意排序的理由：explorer 的 rescue 把 opus-5-5 排在价格更低的 gpt-6.1-sol 之前，因为 Claude Code 里的 explorer 优先 Claude 家族。
  • 擅长点是开放的示例清单：各家族的擅长点写在型号排名表里，价格低也算，想听另一家厂商的意见也算；简单、大量的工作偏向 gpt-6-luna，只在列有它的格里适用。任务落在某个候选的擅长点上时取那个候选。
  • 车道默认顺序只管两件事：几个候选同样合适时的平手，以及候选必须替换时换到谁。Claude Code 中的 explorer 有例外：Claude Code 自带 explorer 但不能指定模型，本插件补上这一块，所以它优先 Claude 候选。这个理由在 Cursor 不成立，所以 Cursor 的 explorer 格按车道顺序排。
  • 档案同时声明按家族定位的能力排名（starter、midrange、premium、flagship）、跨家族的价格链、两条已声明假设及其失效条件。不同家族的型号只按定位比较。升级梯的下限依据这份排名，见第 3 节。

advisor 映射的含义

场合用哪一格
验收形状（第 3 层）mainstay 格的默认拨盘
决策形状（决策类型门）mainstay 格，取默认之后的那一档强度
verdict 自报低置信度crux 格

advisor 的用法由这四条映射固定下来。决策形状比验收形状高一档强度，两者不落在同一拨盘。落到哪份 agent 文件由所选拨盘的强度决定，见第 7 节。

会话续用窗口一节

档案的「Session reuse windows」一节写四个窗口：Claude Code 里发给子代理的 SendMessage 1 小时，codex 车道 30 分钟，grok 车道 1 小时，Cursor 的 Task resume 1 小时。窗口是椰椰声明的续用政策，不是实测的缓存寿命。机制见第 15 节。

Claude Code 部分

到达方式：grok 经 runner，spec 必须同时写 model 与 effort；GPT 经 codex runner；Claude 经本插件的 agent 文件加按次 model，不传 name。claude 拨盘到 agent 文件的映射写在档案里：worker 的 sonnet-5-5[high]、[xhigh] 经 worker-h、worker-xh 加 sonnet；opus-5-5[medium]、[high]、[xhigh] 经 worker-md、worker-h、worker-xh 加 opus。route gate 以 Claude Code 表为准，runner 取两张表的并集（第 14 节、第 6 节）。

Cursor 部分

worker 与 advisor 行与 Claude Code 相同，explorer 行单列。可用性按每个候选的实际调用入口判断：GPT 候选经 Shell 走 codex runner；grok-4.7、Claude 候选与 Cursor 自家模型都经钉型号的 Task。当回合的允许名单只约束钉型号的 Task 派发。型号名（slug）不写进档案，缺席的变体跳过并披露。

易变状态（额度、截止日期）只在开场口头声明，只对当次会话有效，不落盘；没有声明时取格内第一个候选的 * 拨盘。handoff lane 只在用户按任务或按会话声明后进入候选。

如何调整

  1. 只改 plugin/skills/orchestration/routing-profile.md 里的格子。中文文件是译文，不是第二来源。改表时更新文首的声明日期。
  2. 发布插件并在两侧更新（docs/agents/plugin-release.md）；改格算次版本。运行中的会话重启之前仍用旧档案。
  3. 不必改技能正文，也不必跑伴生安装器。任一相关型号换代时重估对应的格子。

本说明书不复述档案的逐格取值与型号排名。那些是用户在声明日写下的判断，随格子而变。

14路由行与 route gate

每次派发都写明路由。runner 的路由是 spec 的字段（第 6 节）；claude 车道和 Cursor 的路由写在提示词里。Claude Code 的 Agent 与 SendMessage 由 route gate 校验。

路由行

claude 车道派发的提示词第一行是路由行，第二行是读取所需前言的指令（按绝对路径）。发给本角色池子代理的每条 SendMessage 消息，第一行也是路由行；暂停、纠正这类消息同样要带。格式：

Route: role=<explorer|worker|advisor> tier=<mainstay|crux|rescue|same-model> dial=<model>[<effort>] basis=<kind> ref=<text to end of line>
  • dial 是档案记法里的一个具体拨盘，例如 opus-5-5[medium]，不写一格里的强度列表；haiku-4-5 不带方括号。
  • mainstay 省略 basis 和 ref。高于它时，basis 是该角色、该档位接受的依据种类（第 2 节的表），ref 写到行尾。
  • 同模派发写 role=worker tier=same-model 与 basis=same-model，ref 写产物类别。

例：Route: role=explorer tier=mainstay dial=haiku-4-5；Route: role=worker tier=crux dial=opus-5-5[medium] basis=key-difficulty ref=three interfaces constrain each other。

route gate

route gate 是插件的 PreToolUse hook。plugin/hooks/hooks.json 以匹配器 Agent|SendMessage 调 plugin/hooks/route-gate.py。它检查 subagent_type 以 fable-advisor: 开头的每次 Agent 派发，和发给本角色池子代理的每条 SendMessage 消息。不合规的调用被 permissionDecision: deny 拒绝，不用 ask。拒绝理由以 fable-advisor route gate: 开头，写明缺了什么；路由行能解析时，理由还列出该角色、该档位的合法拨盘。主代理改正后重发。在无界面会话的 auto 与 bypassPermissions 模式下，拒绝都生效，被拒的子代理不会启动。

route gate 校验提交的配置；子代理实际跑的型号，以子代理记录里的 message.model 为准。每个被检查的调用满足下面八条规则：

规则内容
1 角色路由行的角色与 agent 文件一致：explorer-* 是 explorer，worker-* 是 worker，advisor-* 是 advisor。
2 拨盘每次本角色池 Agent 派发都显式带 model；不带时型号还受 agent 文件的 model: 与 CLAUDE_CODE_SUBAGENT_MODEL 影响，所以拒绝。拨盘由 model 与 agent 文件 frontmatter 的 effort: 推出，路由行写的拨盘必须与推出的相同。别名按顺序解析：别名所属家族与会话型号相同时取会话型号；否则取别名的重定向变量（ANTHROPIC_DEFAULT_HAIKU_MODEL、ANTHROPIC_DEFAULT_SONNET_MODEL、ANTHROPIC_DEFAULT_OPUS_MODEL、ANTHROPIC_DEFAULT_FABLE_MODEL）；都没有时取档案锚点：haiku 为 haiku-4-5，sonnet 为 sonnet-5-5，opus 为 opus-5-5，fable 为 fable-5-1。会话型号读不到时，跳过家族这一步。推出的型号规范化后不是锚点型号时拒绝：会话在 claude-sonnet-4-5 上、派发写 sonnet，就属于这种情况。haiku-4-5 没有强度可比；explorer-h 配 sonnet 按 sonnet-5-5[high] 校验。例外：CLAUDE_CODE_SUBAGENT_MODEL_FORCE 为真值（1、true、yes、on）时，宿主去掉了 Agent 的 model 参数，hook 不要求它，改按 CLAUDE_CODE_SUBAGENT_MODEL 推出拨盘；该变量未设或为 inherit 时取会话型号。
3 档位（角色，拨盘）出现在档案 Claude Code 表里该角色、该档位的格里。
4 依据crux 与 rescue 要有依据：种类按角色和档位合规（第 2 节的表），ref 非空。只查存在与格式，不查真假。mainstay 可以省略依据；写了的话，种类必须是四种之一，ref 非空。
5 同模派发只限 worker-*：tier=same-model，依据种类 same-model，ref 非空。推出的型号必须等于会话型号，并且出现在档案 Claude Code 表的某个格里。会话型号取会话记录里最后一条真实助手记录的 message.model，读不到就拒绝。message.model 为 <synthetic> 的助手记录（宿主在 API 报错等情况下写入）被跳过；全是 synthetic 记录，等于没有助手记录。产物类别与依据的真假仍由主代理判断。
6 name本角色池的派发带 name 键就拒绝（值为字符串、空串或 null 都拒），因为 name 会让 agent 文件的强度失效。
7 SendMessage消息第一行是路由行。拨盘取目标子代理的实际配置：它的记录里最后一条真实助手记录的 message.model 与 effort（规范化）；目标还没有助手记录时，取它的 meta.json（agentType、model），再按规则 2 推出。拒绝理由给出目标的拨盘，主代理照抄即可。放行的情况：只订阅（notify_when_idle 为真、没有消息）；meta.json 的 agentType 不属于 fable-advisor:；目标是名字、main 或别的会话（本角色池不带 name 派发，所以按名字寻址的目标一定不在池里）。目标形如 agentId，却在本会话找不到记录：拒绝。TaskStop 不检查。
8 拒绝字段缺失、格式错误或互相矛盾，拒绝。档案读不出或解析失败，拒绝。输入不是合法 JSON，或出现意外异常，也拒绝。

route gate 覆盖不到的地方

  • Cursor 钉型号的 Task（含 resume）：路由只有文本规则（第 8 节）。Cursor 经 Shell 跑的 codex runner 受 runner 校验。
  • 没有 Python 的机器：hook 放行，stderr 写一行说明，和 receipt gate 一样。
  • 内置代理（general-purpose、Explore 等）不属于本角色池，hook 不管。
  • 会话第一条回复里的同模派发会被拒，因为那时会话记录里还没有助手记录；hook 运行时，本条回复也还没写进记录（第 13 节）。
  • hook 只校验提交的配置，不校验依据是否属实。

档案是唯一来源

route gate 与 runner 都读随插件发布的路由档案，不另建路由配置。解析档案、校验规则、取宿主的值是三件分开的事。Python 解析器（route gate）和 JS 解析器（plugin/scripts/routing-profile.mjs，runner）各有一份，由 tests/test_routing_profile_parity.py 对照一张手写的预期表。档案的表格语法改动时，这条测试先失败；改语法要同时改两个解析器。

15会话续用窗口

车道会话只在续用窗口之内续用。窗口的取值是椰椰声明的续用政策，不是实测的缓存寿命，写在路由档案的「Session reuse windows」一节。

车道窗口时间来源
claude 车道（Claude Code 里 SendMessage 发给子代理）1 小时子代理记录 subagents/agent-<id>.jsonl 里最后一条助手记录的时刻
codex 车道30 分钟runner 回执的 lane_finished_at
grok 车道1 小时runner 回执的 lane_finished_at
Cursor 的 Task resume1 小时主代理在 Task 结果返回时用 Shell（date -u +%Y-%m-%dT%H:%M:%SZ）记进任务件的时刻

窗口从车道上次活动算起。时间不明时，按超出窗口处理：例如 Cursor 上没有记下时刻，窗口就按已过处理。不能用回执的 finished_at，因为它在验证之后才记录。

哪些续用受窗口约束

  • 返工票；
  • 修正契约；
  • 被时钟切断（idle_timeout、timeout）之后的续跑；
  • 发给子代理的后续消息（SendMessage）；
  • 新票。

超出窗口

在同一档位、同一拨盘上新开会话。返工票或修正契约带上缺陷、原契约、上轮报告和回执。新开会话不算升档，失败计数不变。续用时不改强度。runner 车道新开会话时，spec 里省略 resume_session_id。

例外

超出窗口仍要续用时，派发说明要做到四点：

  • 点名原会话独有的可观察状态或证据；
  • 列出已检查的磁盘材料与日志；
  • 说明为何不能靠交接保留这些状态，并写出重建的具体步骤与代价；
  • 披露接受冷缓存的输入成本。

「原会话熟悉代码」或「交接麻烦」不算理由。

新票

新票只在四个条件同时成立时续用已有会话：同一区域、确实需要共享上下文、同一拨盘、在窗口之内；否则新开会话。

没有机械校验

本版不对续用做机械拦截。runner 跨工作目录查不到会话的上次活动，按文件修改时间判断的可靠性也没有证据。将来要做，要先定下：哪些事件算活动、边界时刻、运行中的纠正消息怎么算、例外写在哪个字段。

16全局规划、按结果验收与宽检查（ADR 0030 决策 1 至 3）

椰椰 2026-10-03 报告了 6.1.0 试用中的三个问题，证据来自 cc-usage 的一次会话（2026-10-02 至 10-03，加载 6.1.0）。本节与后两节逐个说明。第一个问题是逐票验证：前端 5 张票逐张派发、逐张验收、逐张提交，下一张等上一张提交后才派；01 与 02 改同一张表，03 与 04 改同一张图表，都没有并成一份契约，而合票规则当时已写在 SKILL.md 里；会话至少跑了 141 次检查，其中定向检查至少 104 次；主代理把「每票验收后提交」作为推荐项提给椰椰，没有给出按契约提交的选项。椰椰 2026-10-04 的说明把重点放在主代理的全局意识上。证据与诊断在 .scratch/trial-6-1-0-feedback/problem-report.md。

派发前做全局规划，只等真实的依赖

改了什么任务有两张以上的票时，主代理在第一次派发前把依赖、契约、隔离、宽检查四项写进任务件。没有全局的阶段屏障：一份契约在它需要的契约验收通过、判定检查就绪后就派发，只有它需要的结果只能由某项宽检查证明时才等这项宽检查。提交仍按授权和回滚边界拆，与验收分开；向椰椰问提交粒度时给出按契约提交的选项。同时进行的契约若共用工作目录，各用独立的工作目录，只换分支名而共用一个工作目录不算隔离；Cursor 的普通 Task 共用工作区，并发契约改用 best-of-n-runner 或依次执行。

为什么椰椰 2026-10-04 的说明要点：关键在主代理要有全局意识；没有依赖关系的票尽量并发，可以用规定修改范围、切分支等方式来限制；测试是某个环节要结束了验收完好进行下一个环节。

依据ADR 0030 决策 1；任务件 .scratch/trial-6-1-0-feedback/spec.md D1 第 1、2 条。Cursor 的隔离是 ADR 0030「决策门核对」第 6 项里主代理补定的。

按结果验收，不只看测试

改了什么第 1 层验收对照契约逐条核对三样东西：报告对每条标准的说法、车道的检查证据、承载 Objective 所述行为的文件的限定路径差异。差异实现的是别的行为时，即使检查全部通过也拒收。差异太大时交 advisor 阅读，主代理核对标准、证据、结论是否一一对应，再读 advisor 标出的片段。第 3 层的触发条件不变。README 的默认验收说明随之改写。

为什么旧写法是接受验证证据加 git diff --stat，测试只证明它覆盖的断言。椰椰要求主代理看子代理交回的结果是否符合要求，不能纯依赖测试来判断。

依据ADR 0030 决策 2；任务件 D1 第 3 条。README 的改动由实施后的 advisor 验收提出。

宽检查一批只跑一次，恢复「共用昂贵准备」

改了什么宽检查包括全量测试、渲染或浏览器检查、端到端套件、完整构建或打包、与其他契约的检查共用昂贵准备（服务、浏览器、设备、构建）的检查，以及主代理自己的渲染和人工检查。每项在它覆盖的契约都落地并验收之后跑一次，只挡需要它结果的工作。一次失败要能归因到一份契约，做不到就把批次分小。契约仍只放本契约的判定检查（ADR 0029 决策 1 不变）。worker 前言同步补上共用准备的检查和调用方自己的渲染、人工检查。

为什么ADR 0029 决策 2 退役了「共用昂贵准备」这个触发词，按条文只覆盖一张票的渲染检查仍归那张票。渲染截图这类检查只覆盖一张票，却共用服务和浏览器，所以恢复这个触发词。票 01 单独做了一轮约 8 分钟的渲染验收。

依据ADR 0030 决策 3，修订 ADR 0029 决策 2；任务件 D1 第 4 条。

17档位准入、路由行与机械校验（ADR 0030 决策 4 至 6）

20升级步骤与注意点

从 6.1.0 升级到 6.2.0 有不兼容改动，下面五处要留意，升级步骤在本节末尾。

runner spec6.1.0 的 spec 没有 role 与 tier，现在判 spec_invalid，不拉起 CLI。给每份 spec 加上 role（implement 用 worker，report 用 explorer 或 advisor）与 tier；高于 mainstay 时再加 basis。

省略的默认值codex spec 省略 model 或 effort 时，runner 按省略默认值补齐后再校验路由。补齐后的拨盘不在该角色、该档位的格里，就判 spec_invalid。省略 model 时补齐为 gpt-6-astra，worker 的 mainstay 格里没有它，所以 tier: mainstay 的 worker spec 会被拒。省略 effort 时按型号补齐，gpt-6.1-sol 补齐为 high：它在 worker mainstay 格里，不在 crux 格里。建议 spec 总是写明 model 与 effort。

grok spec现在必须同时写 model 与 effort；缺一个就判 spec_invalid。

claude 车道提示词与 SendMessage发给本角色池子代理的 Agent 提示词和 SendMessage 消息，第一行必须是路由行，route gate 检查它。第二行是读前言的指令，这只是文本规则，route gate 不检查它是否存在或正确。每次 Agent 派发都要显式带 model，不能带 name；例外是 CLAUDE_CODE_SUBAGENT_MODEL_FORCE 为真值时，宿主去掉了 model 参数，route gate 不要求它，改按 CLAUDE_CODE_SUBAGENT_MODEL（未设或为 inherit 时按会话型号）推出拨盘。路由行、model 或 name 不合规的调用被 route gate 拒绝。

receipt 新字段receipt 多了 role、tier、basis 与 lane_finished_at。按固定键集合严格解析 receipt 的调用方要接受这些键。
