# 编排 —— 角色、档位、车道、姿态

主代理——无论跑什么模型——拥有需求、拆解、交付契约、路由与验收。一次派发是某个角色、某个档位、经由某条车道；姿态决定主代理是否还亲手改交付物。

## 成本纪律 —— 首要指令

**把判断花在稀缺处。** 判断是契约捕捉不到的东西：拆解、接口、保留约束、路由、验收。车道自有的缺陷由车道调试；主代理提供可复现失败，仅当缺陷归属不明时才给假设。

**让体量离开主代理的上下文。** 当阅读面宽、可独立并行、或只有结论属于主线程时，派发 `explorer`；对已知文件的有界查找由主代理自己读。代码块长度、以及能否塞进一次工具调用，都不是派发标准。

**编排姿态下，每一处交付物改动都有作者以外的读者。** `worker` 写；主代理或 `advisor` 读；自己写、自己验收的改动已经离开评审链。

## 姿态

姿态是主代理对交付物的关系。两种姿态，恰好只差一条规则：

- **编排姿态**：交付物只经 `worker` 修改；主代理（此姿态下即架构师）写契约、派发、验收。
- **实现姿态**：主代理可亲手改交付物。

任一角色在两种姿态下都可派发；实现姿态从不意味着「不派发」。

**选择器。** 用户声明或上层指示优先；两者都没有时，存在上游任务件（issue、spec、任务文件）即为编排姿态，否则为实现姿态。

姿态相对一次派发而言：车道对自己的契约处于实现姿态，对它拉起的任何子代理处于编排姿态。深度不限。

## 委派边界 —— 按产物类别

编排姿态下，架构师可否编辑一个文件，取决于该文件是什么，从不取决于改动看起来有多小。

- **交付物**：随产品发布、被测试行使、或向用户描述行为的产物。一律经 `worker`，无论大小；一行修复不是例外。
- **协调件**：任务、issue 与 spec 文件；决策记录；工作流状态文件；发布版本字段。任一姿态下都直接写。

仓库的路径映射写在其 AGENTS.md 或等价物中。类别不清则按交付物处理。

**同模派发** 是 `claude lane` 的一个拨盘：模型钉为会话模型。仓库的 AGENTS.md 写明它服务哪一类产物。只有 `worker` 用它；它的路由是档位 `same-model`、依据种类 `same-model`，`ref` 写那一类产物。Cursor：`generalPurpose` 且不带 `model`（inherit）。Claude Code：某个 `worker-*` agent，每次派发的 `model` 设为会话模型。

## 角色与档位

角色是契约形状（输入、权限、产出），不点名模型；档位是能力等级，与角色正交。

| 角色 | 权限 | 返回 |
|---|---|---|
| `explorer` | 只读 | 证据：`file:line`、符号、原文 |
| `worker` | 在契约的 Files 范围内写入 | diff 外加核验证据 |
| `advisor` | 只读 | 不超过 300 词的裁决，两种请求形状：**decision**（承诺前：决定、约束、选项）或 **acceptance**（完成后：契约、diff、receipt → 标准是否满足？） |

档位：`mainstay`（主力）、`crux`（攻坚）、`rescue`（后援）；任一角色可配任一档位。档位按角色、型号、强度划分：一个档位是每个角色的一组拨盘，同一型号可以按强度分在不同档位。多数工作在 `mainstay` 结束；`rescue` 很少用到。一次升档（升级梯 R2）在接管契约下运行：接管是契约形状，不是档位。`advisor` 的权威来自它读到的代码，不来自档位。

## 车道

车道回答如何到达一个供应商；角色与档位回答派什么。

| 车道 | 机制 |
|---|---|
| `grok lane` | 经 grok runner（Claude Code）或钉死派发（Cursor）到达 Grok 家族 |
| `codex lane` | 经 codex runner 到达 GPT 家族；model 与 effort 从其白名单可选 |
| `claude lane` | Claude 子代理，按（角色，effort）每组一份 agent 文件：effort 只从该文件来，派发时的 `model` 选定填充。无外部 CLI。从 Claude 主代理出发时披露：同族（无跨厂评审）、共享 Anthropic 额度 |
| `handoff lane` | 用户把 spec 文件带到自选 harness；见 [handoff-lane.md](handoff-lane.md) |

### Harness 机制

按你所在的宿主及其工具的参数结构识别 harness，从不按某一个工具名或是否存在 `model` 参数来认；首次派发之前阅读对应的 lanes 文件：

- Claude Code（runner、receipt、receipt gate、report mode）：[lanes-claude-code.md](lanes-claude-code.md)
- Cursor（钉死派发、经 Shell 的 codex runner、生命周期）：[lanes-cursor.md](lanes-cursor.md)

执行侧契约有两份：[lane-preamble.md](lane-preamble.md) 给 `worker`，[lane-preamble-report.md](lane-preamble-report.md) 给 `explorer` 或 `advisor`。runner 前置 `mode` 所指的那份；Cursor 派发指向其角色所需的那份。两份都不要重述。

## 路由 —— 两阶段

**阶段 1 —— 选（角色, 档位）。** 角色按产出选。档位按任务难点或升级梯定：新工作从 `mainstay` 开始；已识别关键难点，或要处理相互制约的条件时，首轮可以直接用 `crux`，不设使用比例；`rescue` 不作首轮选择，除非用户声明；升档按升级梯。

用户声明的家族或型号只筛选候选，不定档位。取满足三个条件的最低一档：不低于按难点或升级梯定下的档位；该格有兼容候选，即符合声明的候选；准入允许，即这次派发带有该档位对该角色接受的一种依据（`mainstay` 不需要依据）。用户对型号或家族的声明，可以作为 `user-declaration` 依据准入 `crux`，`ref` 写用户原话；它从不准入 `rescue`。三个条件同时满足不了时，向用户报告冲突；绝不自动降档。

**路由。** 每次派发都写出路由：角色、档位、拨盘；高于 `mainstay` 时再写依据，格式按对应的 lanes 文件。经 `SendMessage` 或 `resume` 发给已有会话的消息，也要写出路由。各角色、各档位接受的依据种类：

| 角色 | `crux` | `rescue` |
|---|---|---|
| `worker`、`explorer` | `key-difficulty`、`failure`、`user-declaration` | `failure`、`user-declaration` |
| `advisor` | `low-confidence`、`user-declaration` | `user-declaration` |

依据带一条非空的 `ref`：`key-difficulty` 写难点；`failure` 写失败那次派发的标识（receipt 哈希、session id 或 agentId）；`low-confidence` 写报告低置信的那条裁决；`user-declaration` 写用户原话。同模派发有自己的路由（见「委派边界」）。路由在 lanes 文件指明的地方受机械校验。校验只查依据存在且格式合规，不查真假；真假仍由主代理判断。

**阶段 2 —— 格内选择。** 第一个候选是默认；没有声明时取它的 `*` 拨盘。任务落在档案为某个候选声明的擅长点上时选它（价格低也算擅长点）。几个候选同样合适，或需要替换候选时，按档案声明的车道顺序。

**改道。** 不可用或超时的候选（整条车道、单个候选，或 codex runner 启动失败），其契约原样转到同一格的另一个候选，按档案声明的车道顺序，并披露；这不算能力失败。两条 CLI 车道都挂了 → `claude lane`，并说明跨厂评审上的任何损失。可用性由派发决定，而非探测。

**升级 —— 升级梯。** R1：一次验收失败得到返工票，同拨盘，在续用窗口之内用同一会话；契约缺口得到修正契约，条件相同；超出窗口时见「会话续用」。R2：返工票也失败且原因是能力 → 记一次能力失败，升到下一档（`mainstay` → `crux` → `rescue` → 用户）：新会话、接管契约（原契约、先前报告、receipt）。在下一档里按任务特点选型号，新型号在档案排名中不低于失败的型号，除非没有别的候选；同一型号必须提高 effort；不同型号之间不比较 effort 名。R3：同一型号最多提升一次，按完整模型标识计数。R4：执行时的较大问题（工具反复失败、跑飞、触碰保留项）可跳过返工票，记一次能力失败（进入下一档）。环境问题和契约缺口不算失败。首轮就在 `crux` 的任务在 `crux` 失败一次即进 `rescue`；`rescue` 失败交给用户。

## 用户路由 profile

阶段 2 的输入只作为声明进入。

**持久判断。** **填充表**，（角色, 档位）→ 候选车道与拨盘，以及专长备注，写在 [routing-profile.md](routing-profile.md) 里，这是随本技能发布的用户路由档案。首次分配模型前阅读，档案变化或滑出上下文时再读；读不到 → 上报缺口，不做任何假设。`dial` 记作 `model[a*, b, c]`：该格内这一型号可选的 effort，`*` 标默认，没有 `*` 时以第一个列出的为默认；没有 effort 维度的型号裸写。

**易变状态**（额度余额、时限压力）在开工时口头声明，只对该会话有效，从不写入磁盘。

**handoff 声明**（按任务或按会话）独自使 `handoff lane` 在阶段 2 可选；主代理可以对大、已完全确定、且不紧急的工作建议它；建议从不构成路由。

**低置信逃生口。** 仅在两种情况下于路由前询问用户，并给出至少两个带理由的选项：已声明的约束在决定维度上冲突；或任务高风险（正确性关键或难以逆转）且 profile 对此沉默；并行批次每批最多问一次。

## 交付契约

各车道完全不共享你的上下文。每次派发携带五个部分：

1. **Objective**：结果及其验收标准，不是步骤
2. **Files**：拥有的范围（路径或目录）；范围内新增文件允许
3. **Interfaces**：结果必须匹配的共享或对外契约；可为 none
4. **Constraints**：保留项：不得改的东西、上游已钉死的选择，以及调用方留在自己会话里的操作；这些约束车道、它的子代理，以及它的核验命令
5. **Verification**：对 `worker`，范围限于*这一张*契约的改动及其调用方的检查——至少一条 Objective 点名的行为未达成就会失败、且永不延后的检查，先用能做到这一点的最便宜检查（现有测试，文本类改动用 grep），之后才写新的测试代码——不放批次检查，票据列出的也不放；对 `explorer` 或 `advisor`，期望的证据或裁决形状，可为空

Constraints 未规定的一切都是车道的决定。步骤默认不写：只有当上游决策已经钉死序列时，或作为失败返工票之后的定向指导时才写。

**契约缺口与实现选择。** 契约缺口（预期行为不明、要求冲突、须改动的保留接口、无法判定什么算通过）作为报告返回，并得到修正后的契约。未规定的实现选择（内部函数划分、等价数据结构、测试组织、范围内的错误处理）归车道，不上报、不等待。

**上游任务件。** 当 issue、spec 或任务文件存在时，契约引用其路径，并只内联验收标准、保留约束和本契约自己的检查，写明哪些节是约束性的。主代理既不重述也不重新规划。

**返工票。** 给同一条车道的新契约，在续用窗口之内复用其会话：Objective = 缺陷（违反的要求、可复现失败、期望行为、证据）；Files = 原范围；Verification = 能覆盖失败用例和修复波及范围的最小可运行检查，不是整个套件。里面不写修复方案。理由：违反的要求、可复现的问题、缺失的核验、受影响的保留接口；从不是结构偏好。

**会话续用。** 车道会话只在该车道的续用窗口之内续用：返工票、修正契约、被时钟切断后的续跑、发给子代理的后续消息、新票，都是如此。窗口取值写在路由档案的「会话续用窗口」一节。窗口从车道上次活动算起，时间取自 lanes 文件指明的可追溯来源；时间不明时，按超出窗口处理。超出窗口时，在同一档位、同一拨盘上新开会话；返工票或修正契约带上缺陷、原契约、上轮报告和 receipt。新开会话不算升档，失败计数不变。续用时从不改强度。例外：超过窗口仍要续用时，派发说明要点名只有原会话持有的可观察状态或证据，列出已检查的磁盘材料和日志，说明为何不能通过交接保留，写出重建的具体步骤和代价，并披露本次接受冷缓存的输入成本；仅以「原会话熟悉代码」或「交接麻烦」为由，不满足例外。新票只有在同一区域、确实需要共享上下文、同一拨盘、在窗口之内时，才续用已有会话；否则新开会话。

## 并行

**派发前做全局规划。** 任务有两张以上的票时，在第一次派发前把规划写进任务件：

- 依赖：哪张票需要另一张票的结果，例如接口，或在同一文件上接着改；
- 契约：共用文件或同一区域的多张票交给一个 `worker`，作为一张契约派发，每张票各有一条判定检查和一行报告；以下情况分开派发：超出一条车道的上下文、一张票需要另一张已核验的结果、一张票需要单独授权。这张契约验收一次，不逐票验收；
- 隔离：每张契约的修改范围（Files）；同时进行、会共用一个工作目录的契约，各在一个独立的工作目录里运行（见对应的 lanes 文件）；只换分支而共用一个工作目录，不算隔离；
- 宽检查：每一项覆盖哪些契约、由谁跑、在什么时点跑（见「每条检查只跑一次」）。

**只等真实的依赖。** 没有全局阶段屏障。相互独立的契约（无共享文件、无顺序依赖）在同一条消息中作为并行车道启动；顺序链与单文件手术保持串行。一张契约在它需要的契约验收通过、它的判定检查就绪后就派发，不等无关的契约。只有它需要的结果只能由某项宽检查证明时，它才等这项宽检查。一张独立契约的验收、返工和检查，从不挡另一张契约的派发。

提交只在授权或回滚边界处拆分，与验收分开安排。向用户询问提交粒度时，要给出按契约提交的选项。

对利害重大的工作，让两种填充对同一契约竞速并挑选更强的 diff；来自主代理以外家族的两种填充，以多一条车道的成本买到*第三个*视角。同一工作树上的两个执行者会互相覆盖；竞速把每种填充的工作目录与执行记录隔离开（见对应的 lanes 文件）。

## 决策类型门

在这些决策类型上咨询 `advisor`；本清单约束任一主代理、任一档位、任一姿态：

- 承诺一种架构、数据迁移、API 形态或重构策略
- 推翻既定计划
- 改动公共接口或跨模块依赖
- 放宽验收标准
- 同一问题已失败两次

全部取 **decision** 形状：交出决定、约束和选项；`advisor` 自己读代码。**acceptance** 形状经核验的第 3 层到达，从不按步数。按裁决行事，或把分歧摊开；绝不明吞忽略。无机械强制，无逐 diff 评审。

## 核验

报告是主张，不是证据；评审对象是契约，而验收一张契约结清的是这张契约，不是整个任务。三层：

1. **第 1 层 —— 默认每条车道。** 对照契约逐条核对三样东西：报告对每条验收标准的说法；车道的检查证据（命令、退出码、输出尾部，对照工作树抽查）；承载 Objective 所述行为的文件按路径限定的 `git diff <file>`，这些文件经 `git diff --stat` 找出。测试证明它覆盖的断言，不证明整张契约：差异实现的是另一种行为时，即使每条检查都通过，验收也不通过。差异太大读不下时，交 `advisor` 阅读；主代理核对标准、证据、结论是否一一对应，并读 `advisor` 标出的片段。完整的未限定范围 `git diff` 从不进入主代理上下文。车道自己做的评审或验收是主张；复用它的命令输出，不重跑，把验收的力气花在车道看不到的部分：其他契约、它不具备的环境、批次检查。
2. **第 2 层 —— 具体怀疑。** 当报告、stat 或核验输出引起具体怀疑时，读它所指向的其他文件按路径限定的 `git diff <file>`。当车道自己写了验收测试时，读它：它是主张的一部分，不是证据。
3. **第 3 层 —— 正确性关键工作、同族 diff，以及用户要求评审。** `advisor` 取其 acceptance 形状（上下文干净、只读、读 diff 加 receipt）返回裁决与标记出的 hunk；只读那些。对同族 diff 优先用跨厂填充。裁决仍是主张；主代理保留最终判断。

**每条检查只跑一次。** 一张契约的检查列表只有一个执行者——由对应的 lanes 文件点名是谁——不为收尾再跑一遍；列表里保留这张契约的判定检查。宽检查即批次检查：全量测试、渲染或浏览器检查、端到端套件、完整构建或打包、与其他契约的检查共用昂贵准备（服务、浏览器、设备或构建）的检查，以及主代理自己做的渲染或人工检查。每项宽检查在它覆盖的契约都落地并验收之后跑一次；只在它发现的失败返工之后再跑。它只挡需要它结果的工作。一个批次容纳的契约数，以一次失败仍能归因为限；失败时给追溯到的致因契约开返工票，追溯不到某一张契约时，把这一批分小。批次检查在任务件里登记一次，记为通过、失败或待跑，并附输出；有失败或待跑的批次检查（包括因提前停止而没跑的），任务就不算完成，除非用户豁免。主代理可以把一个批次的执行交给车道；裁决仍归它自己。证据在其背后的代码、输入与环境未变时持续有效：换角色或换会话本身不是重跑的理由。

「应该能用」「测试应该能过」，或背后没有命令输出的验收，意味着未完成。
