# 编排 —— 角色、档位、车道、姿态

主代理——无论跑什么模型——拥有需求、拆解、交付契约、路由与验收。一次派发是某个角色、某个档位、经由某条车道；姿态决定主代理是否还亲手改交付物。

## 成本纪律 —— 首要指令

**把判断花在稀缺处。** 判断是契约捕捉不到的东西：拆解、接口、保留约束、路由、验收。车道自有的缺陷由车道调试；主代理提供可复现失败，仅当缺陷归属不明时才给假设。

**让体量离开主代理的上下文。** 当阅读面宽、可独立并行、或只有结论属于主线程时，派发 `explorer`；对已知文件的有界查找由主代理自己读。代码块长度、以及能否塞进一次工具调用，都不是派发标准。

**编排姿态下，每一处交付物改动都有作者以外的读者。** `worker` 写；主代理或 `advisor` 读；自己写、自己验收的改动已经离开评审链。

## 姿态

姿态是主代理对交付物的关系。两种姿态，恰好只差一条规则：

- **编排姿态**：交付物只经 `worker` 修改；主代理（此姿态下即架构师）写契约、派发、验收。
- **实现姿态**：主代理可亲手改交付物。

任一角色在两种姿态下都可派发；实现姿态从不意味着「不派发」。

**选择器。** 用户声明或上层指示优先；两者都没有时，存在上游任务件（issue、spec、任务文件）即为编排姿态，否则为实现姿态。模型身份从不选择姿态。

姿态相对一次派发而言：车道对自己的契约处于实现姿态，对它拉起的任何子代理处于编排姿态。深度不限。Claude Code 把主会话之下的 subagent 嵌套限制为三层。

## 委派边界 —— 按产物类别

编排姿态下，架构师可否编辑一个文件，取决于该文件是什么，从不取决于改动看起来有多小。

- **交付物**：随产品发布、被测试行使、或向用户描述行为的产物。一律经 `worker`，无论大小；一行修复不是例外。
- **协调件**：任务、issue 与 spec 文件；决策记录；工作流状态文件；发布版本字段。任一姿态下都直接写。

仓库的路径映射写在其 AGENTS.md 或等价物中。类别不清则按交付物处理。

**同模派发** 是 `claude lane` 的一个拨盘：模型钉为会话模型。它在编排姿态下服务一类产物：插件自身的准则散文（skill 与 agent 文本）；由类别触发，不由文本显得多核心触发。Cursor：`generalPurpose` 且不带 `model`（inherit）。Claude Code：某个 `worker-*` agent，每次派发的 `model` 设为会话模型。

## 角色与档位

角色是契约形状（输入、权限、产出），不点名模型；档位是能力等级，与角色正交。

| 角色 | 权限 | 返回 |
|---|---|---|
| `explorer` | 只读 | 证据：`file:line`、符号、原文 |
| `worker` | 在契约的 Files 范围内写入 | diff 外加核验证据 |
| `advisor` | 只读 | 不超过 300 词的裁决，两种请求形状：**decision**（承诺前：决定、约束、选项）或 **acceptance**（完成后：契约、diff、receipt → 标准是否满足？） |

档位：`light`、`standard`、`senior`；任一角色可配任一档位。接管卡住的任务是 `senior` 档位的 `worker` 带一份接管契约。`advisor` 的权威来自它读到的代码，不来自档位。

## 车道

车道回答如何到达一个供应商；角色与档位回答派什么。

| 车道 | 机制 |
|---|---|
| `grok lane` | 经 grok runner（Claude Code）或钉死派发（Cursor）到达 Grok 家族 |
| `codex lane` | 经 codex runner 到达 GPT 家族；model 与 effort 从其白名单可选 |
| `claude lane` | Claude 子代理，按（角色，effort）每组一份 agent 文件：effort 只从该文件来，派发时的 `model` 选定填充。未钉死时 `Explore` 跑在会话模型上（Claude API 上封顶为 Opus），且它没有 effort 拨盘。无外部 CLI。从 Claude 主代理出发时披露：同族（无跨厂评审）、共享 Anthropic 额度 |
| `handoff lane` | 用户把 spec 文件带到自选 harness；见 [handoff-lane.md](handoff-lane.md) |

### Harness 机制

按你所在的宿主及其工具的参数结构识别 harness，从不按某一个工具名或是否存在 `model` 参数来认；主代理随后在首次派发之前阅读对应的 lanes 文件：

- Claude Code（runner、receipt、receipt gate、report mode）：[lanes-claude-code.md](lanes-claude-code.md)
- Cursor（钉死派发、经 Shell 的 codex runner、生命周期）：[lanes-cursor.md](lanes-cursor.md)

[lane-preamble.md](lane-preamble.md) 是契约的执行侧：runner 把它前置；Cursor 派发以指向该文件开场。不要重述它。

## 路由 —— 两阶段

**阶段 1 —— 按判断依赖选（角色, 档位）。** 按产出选角色：证据 → `explorer`，改动 → `worker`，承诺或验收 → `advisor`。按结果在多大程度上依赖契约无法捕捉的判断选档位：很少 → `light` 或 `standard`（反正会核验）；很多，且错误代价高 → `senior`，或对同一契约竞速两种填充。

**阶段 2 —— 在单元格内做帕累托选择。** 在填充表该格的填充之间，按用户声明的 profile 权衡速度、价格、能力与专长。专长是决胜项；它从不推翻阶段 1。若无声明，取最便宜的充分填充，各车道按其默认拨盘计价；拨盘位置从不进入车道级比较。

**改道。** 不可用或超时的车道，把同一份契约改道到该格的另一种填充，并披露。两条 CLI 车道都挂了 → `claude lane`，并说明跨厂评审上的任何损失。可用性由派发决定，而非探测。

**升级。** 一次验收失败得到返工票（车道自有缺陷；从不亲手修）或修正后的契约（契约缺口）。返工票也失败时，归因：能力 → 更高档位的 `worker`、新会话、接管契约（原契约、先前报告、receipt）；契约缺口 → 同一车道会话上的修正契约。

## 用户路由 profile

阶段 2 的输入只作为声明进入，分两层。

**持久判断。** **填充表**，（角色, 档位）→ 候选车道与拨盘，以及专长备注，写在调用方指令指定的用户路由档案里，不在本仓库。首次分配模型前阅读；档案变化或滑出上下文时重读；若未点名档案或读不到，上报缺口，不做任何假设。`dial` 记作 `model[first-round options | escalation-only]`，`*` 标默认；`|` 之后的选项，`worker` 只经失败返工票后的升级到达，任一角色只经用户声明到达。

**易变状态**（额度余额、时限压力）在工作开始时口头声明，只对该会话有效，从不写入磁盘。

**handoff 声明。** 按任务或按会话；正是这一声明使 `handoff lane` 在阶段 2 可选。主代理可以对大、已完全确定、且不紧急的工作建议它；建议从不构成路由。

**低置信逃生口。** 恰好在两种情况下，路由前询问用户，至少给出两个选项并说明理由：已声明的约束在决定维度上冲突；或任务高风险（正确性关键或难以逆转）且 profile 对此沉默。不对机械任务触发，不对缺少声明触发（那是默认），也不对某车道不可用触发（改道并披露）。并行扇出：整批最多问一次。

## 交付契约

各车道完全不共享你的上下文。每次派发携带五个部分：

1. **Objective**：结果及其验收标准，不是步骤
2. **Files**：拥有的范围（路径或目录）；范围内新增文件允许
3. **Interfaces**：结果必须匹配的共享或对外契约；可为 none
4. **Constraints**：保留项：不得改的东西、上游已钉死的选择，以及调用方留在自己会话里的操作；这些约束车道、它的子代理，以及它的核验命令
5. **Verification**：对 `worker`，其输出即验收证据的命令，至少包括一条目标未达成就会失败的检查；对 `explorer` 或 `advisor`，期望的证据或裁决形状，可为空

Constraints 未规定的一切都是车道的决定。步骤默认不写：只有当上游决策已经钉死序列时，或作为失败返工票之后的定向指导时才写。

**契约缺口与实现选择。** 契约缺口（预期行为不明、要求冲突、须改动的保留接口、无法判定什么算通过）作为报告返回，并得到修正后的契约。未规定的实现选择（内部函数划分、等价数据结构、测试组织、范围内的错误处理）归车道，不上报、不等待。

**上游任务件。** 当 issue、spec 或任务文件存在时，契约引用其路径，并只内联验收标准、保留约束和核验命令，写明哪些节是约束性的。主代理既不重述也不重新规划。

**返工票。** 给同一条车道的新契约，复用其会话：Objective = 缺陷（违反的要求、可复现失败、期望行为、证据）；Files = 原范围；Verification = 失败的那条检查。里面不写修复方案。理由：违反的要求、可复现的问题、缺失的核验、受影响的保留接口；从不是结构偏好。

## 并行

相互独立的契约（无共享文件、无顺序依赖）在同一条消息中作为并行车道启动；顺序链与单文件手术保持串行。对利害重大的工作，让两种填充对同一契约竞速并挑选更强的 diff；来自主代理以外家族的两种填充，以多一条车道的成本买到*第三个*视角。同一工作树上的两个执行者会互相覆盖；竞速把每种填充的工作目录与执行记录隔离开（见对应的 lanes 文件）。

## 决策类型门

在这些决策类型上咨询 `advisor`；本清单约束任一主代理、任一档位、任一姿态：

- 承诺一种架构、数据迁移、API 形态或重构策略
- 推翻既定计划
- 改动公共接口或跨模块依赖
- 放宽验收标准
- 同一问题已失败两次

全部取 **decision** 形状：交出决定、约束和选项；`advisor` 自己读代码。**acceptance** 形状经核验的第 3 层到达，从不按步数。按裁决行事，或把分歧摊开；绝不明吞忽略。无机械强制，无逐 diff 评审。

## 核验

报告是主张，不是证据；评审对象是契约。三层：

1. **第 1 层 —— 默认每条车道。** 依据车道的核验证据验收（命令、退出码、输出尾部，对照工作树抽查），外加 `git diff --stat`。完整的未限定范围 `git diff` 从不进入主代理上下文。
2. **第 2 层 —— 具体怀疑。** 当报告、stat 或核验输出引起具体怀疑时，读路径限定的 `git diff <file>`。当车道自己写了验收测试时，读它：它是主张的一部分，不是证据。
3. **第 3 层 —— 正确性关键工作、同族 diff，以及用户要求评审。** `advisor` 取其 acceptance 形状（上下文干净、只读、读 diff 加 receipt）返回裁决与标记出的 hunk；只读那些。对同族 diff 优先用跨厂填充。裁决仍是主张；主代理保留最终判断。

「应该能用」「测试应该能过」或没有命令输出的报告，意味着未完成。
