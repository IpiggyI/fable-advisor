# 0035 — 车道退出前自检、不设总时长上限、Files 写具体路径、宽检查复跑收紧

- **Status**: accepted（2026-10-18 椰椰要求调整插件以减少 cc-usage 两次长任务里出现的问题；未发布，版本定为 6.6.0）
- **Date**: 2026-10-18
- **影响范围**:
  - `plugin/scripts/run-grok.mjs`、`plugin/scripts/run-codex.mjs`：注入车道 prompt 的检查列表说明句。
  - `plugin/skills/orchestration/lane-preamble.md`：`**Verification.**` 段。
  - `plugin/skills/orchestration/runners.md`：`timeout_sec` 条目，「runner 是检查列表的执行者」一段。
  - `plugin/skills/orchestration/SKILL.md`：交付合同第 2、5 部，`## Parallelism` 的计划条目，`**Run each check once.**` 段。
  - 两条 runner 的运行中标记（`.fable-advisor/running/<spec_hash>.json`）：新增 `session_id` 字段。
  - 两条 runner 的停止流程（`killProcessTree`）：POSIX 上先发 SIGINT，宽限期后再发 SIGKILL。
  - 以上 `.md` 在 `docs/zh/` 下的孪生；`tests/test_runner_contract.py` 断言注入句的用例。
- **关联**: 修订 [ADR 0020](./0020-one-executor-per-check-list.md) 决策 1（车道不把列表当收尾再跑）；触发的是 ADR 0020 复盘条件第 4 条（`verification_failed` 占比上升）。[ADR 0009](./0009-grok-lane-dewrapper-runner.md) 决策 1（静默截止、`timeout_sec` 无默认值）不变，本次补上主代理何时可以写 `timeout_sec`。[ADR 0029](./0029-scoped-contract-checks-and-batch-defaults.md) 的批次规则不变，本次只收紧复跑。调查件 `.scratch/cc-usage-task-duration/`（问题报告第 1、4、7 节，问题单 01、03、04）。

## 背景

调查对象是 cc-usage 的两次长任务：S1 508 分钟、14 次 Grok 车道运行；S2 341 分钟、14 次 Codex 车道运行。和插件有关的四个现象都已核实：

1. 5 张 `verification_failed` 回执里 4 张有 `bun run typecheck` 失败，报错都在测试文件。车道没跑类型检查，因为 runner 注入句写着「do not repeat this list as a closing step」，`lane-preamble.md` 又把整个项目的慢速类型检查归给主会话。这次类型检查一次 4 秒，而每次失败都要多派一轮返工、主会话多等一轮。
2. S1 主会话给每份 Grok 契约写了 1200 到 3000 秒的 `timeout_sec`，依据是 cc-usage 的一条项目记忆。三条车道在 45 到 50 分钟被 `SIGKILL`，被杀时仍在吐事件（`max_idle_ms` 112 到 151 秒），收尾检查被跳过，只能续跑。
3. 车道全部串行。S1 的 C1 与 C2 的 Files 不相交，仍是一个跑完才派下一个；C3、C5、C6、C7 的 Files 写成整个 `src/`，任何两份都相交。
4. S2 主会话跑了 11 次约 400 秒的全量测试。其中 4 次是执行失误：环境变量泄漏造成假红、返工车道还在跑就开跑、输出被 `tail -15` 截断后为看失败用例名重跑、参数写成 `test/`。另有 2 到 3 次本可以只跑失败的测试文件。

## 决策

1. **车道退出前，列表里每条命令都要在它最后一次相关修改之后通过过。** 两条 runner 的注入句与 `lane-preamble.md` 的 `**Verification.**` 段同步改：runner 收尾时照旧自己跑一遍，这一遍仍是回执里唯一的证据；车道在退出前，对列表里自上次相关修改后还没见过通过的命令，各跑一次。范围内的失败车道自己修；被保留操作或环境挡住的写进 GAPS。列表外、比改动更宽的检查仍归主代理的批次。取舍：廉价检查会执行两次，换来的是少一轮返工。`runners.md` 里「所以车道被告知不要重复」一句随之改写。
2. **契约第 5 部带上廉价的类型检查。** 改动可能破坏项目的类型检查或 lint，而它又廉价时，它进入这份契约的检查列表。否则决策 1 管不到它。
3. **`timeout_sec` 只在当前请求给出时限时才写。** 项目记忆或项目笔记里的取值不算。静默截止只看事件是否停止：一条车道持续吐事件却没有进展，它会一直跑下去。所以主代理在长车道运行期间，读它最新的一行进度和工作树的改动（runner 不写事件日志文件）；判断失控时，按 `runners.md` 的中途停止流程用 `kill <pid>` 停它。只有事件在继续而工作树不变，不算失控；主代理去 CLI 自己的会话记录里读车道最新的输出（Grok：`~/.grok/sessions/<URL 编码的工作目录>/<会话编号>/events.jsonl`；Codex：`$CODEX_HOME/sessions/<年>/<月>/<日>/rollout-<时间>-<会话编号>.jsonl`），看到车道在原地重复才停。记录按会话编号找，编号取自运行中标记的 `session_id`（决策 6）。两条路径是 2026-10-18 在本机核实的 CLI 磁盘布局，runner 不检查它们；CLI 升级后先 `ls` 这两个目录复核。
4. **实施契约的 Files 写具体路径。** 只有契约要在某个目录下新建文件时，Files 才写这个目录。原因是 Files 决定哪些契约能同时跑。报告模式契约的 Files 仍是读取范围，不受这条约束。并行计划里，两份契约串行要写明理由：共用文件、需要对方的结果、容量限制，或有证据的环境限制。同时运行的契约仍各用独立工作目录。
5. **宽检查的复跑收紧。** 宽检查的完整输出写进文件，失败从文件里读，不从截断的末尾读。写入它覆盖范围的车道全部退出后，它才开跑。它发现的失败返工后，先跑失败的测试文件；这一批最后一次返工落地后，宽检查再跑一次。之后的改动若让代码、依赖、输入或环境变了，旧证据随之失效，宽检查仍要重跑；本条不设「小改动只跑定向检查」的例外：后来的改动让旧证据失效时，只跑定向检查会漏掉集成回归。
6. **运行中标记带上会话编号。** 两条 runner 的运行中标记新增 `session_id`：Grok 车道在启动时就知道编号（runner 注入或取自 `resume_session_id`）；Codex 车道在读到编号之前为 `null`，读到之后随下一次刷新写入。原因：标记里没有编号时，只能按「最近修改」去猜会话记录，续跑的车道会被排除，并发时会找到另一条车道，按错记录 `kill` 会停掉正常的车道。椰椰 2026-10-18 在「只改文字、新开车道找不到记录就交给用户」与本做法之间选了本做法。
7. **停车道时先让 CLI 自己收尾。** 中断、静默截止、`timeout_sec`、`preparation_stalled` 四条路径在 POSIX 上先向 CLI 的进程组发 SIGINT，等 5 秒宽限期，仍未退出再发 SIGKILL；Windows 的 `taskkill /F` 不变。2026-10-18 本机探针（临时目录里直接按 runner 的参数启动 CLI，只读小任务，中途发信号）：Grok 收到 SIGINT 0.4 秒退出、退出码 130，两种信号下都不写 `turn_completed`；Codex 收到 SIGINT 0.2 秒退出，会话记录以 `turn_aborted` 结尾并写入进行中的消息，SIGKILL 时没有 `turn_aborted`。5 秒是实测退出时间的十倍以上。Grok 被停回合的用量仍不进 cc-usage 的库，那是 cc-usage 采集器的问题（问题报告第 5 节第 1 条）。椰椰 2026-10-18 提出，并决定并入本版。

## 未采纳

- **runner 遇到 `timeout_sec` 时打印警告。** 规则写进 `runners.md` 已经够用；警告由 runner 发出时，派发已经写好，改不了主会话已经采用的取值。`timeout` 回执再出现被杀时仍活跃的车道，再议。
- **默认让 Grok 车道并发。** cc-usage 的记忆报告过四条 Grok 车道并发时约 20 分钟被硬切（2026-09-05，Grok 1.0.50）。这条没有复核，所以本次只要求写明串行理由，不推并发。
- **收尾检查只差类型错误时由主会话直接修。** 椰椰 2026-10-18 提出，决定先观察。按回执算，两次任务的 4 轮类型检查返工每轮 2.5 到 6.2 分钟（写返工票 0.3 到 0.7 分钟，车道 2.2 到 5.5 分钟），合计约 15 分钟；主会话自己修省不了多少，还要放宽编排姿态「主代理不改交付物」这条规则。决策 1 让车道退出前自己跑类型检查，这类返工的来源应当消失。需要时可在任务开头声明实施姿态，不必改插件。
- **问题单 02（超时车道步数多）与 05（10-15 Grok 每次工具调用多出约 3 秒）。** 原因都没有查实，本次不改插件。两张单仍是 `needs-triage`，各自的探针写在单里。

## 决策门核对

本次命中决策类型门的「推翻既定方案」（ADR 0020 决策 1）。2026-10-18 以 decision 形状咨询 advisor（codex 车道报告模式，`gpt-6.1-sol[high]`，submitted, not observed，会话 `01a14f5e-367e-7a81-a742-f1d2e1afc464`）。2026-10-18 的 acceptance 复审都用 codex 车道 `gpt-6.1-sol[medium]`（submitted, not observed）。第一次（会话 `01a14f74-e700-7631-b1fc-1de622a7e91f`）指出 `runners.md` 的失控判据过强、`SKILL.md` 一句有歧义，两张返工票修正；第三次（会话 `01a14f8d-9de0-7852-84f1-0611484df728`）判决策 1 到 7 全部满足。第二次（会话 `01a14f7a-4d8c-7a11-8ce5-297a521392da`）指出按「最近修改」定位会话记录会找错车道，由决策 6 处理。首次裁决：四项修改后接受。修订全部并入：`timeout_sec` 规则补上静默截止管不到无进展长跑的风险（决策 3）；自检的条件改为「最后一次相关修改后有通过证据」，并同步 `runners.md` 的执行者表述，再加上类型检查进契约（决策 1、2）；Files 规则限于实施契约，串行理由允许容量与环境限制（决策 4）；删掉「小改动只跑定向检查」的绝对规则（决策 5）。

## 复盘条件

- `verification_failed` 回执里，失败的命令车道在报告里自称跑过并通过 → 自检规则被绕过，考虑让 runner 在列表失败时把车道报告里的命令与回执对比。
- `timeout` 回执再次出现，而 spec 的 `timeout_sec` 不来自用户的当前请求 → 规则没到达主会话，考虑 runner 侧机制。
- 出现持续吐事件、长时间没有进展的车道，靠人工发现才停 → 静默截止不够，另找进展信号。
- 下一次长任务里，`verification_failed` 仍有一半以上只差类型检查或 lint → 重议「主会话直接修」的窄例外：只限收尾检查里的类型或 lint 错误、改动几行、文件都在契约 Files 内，由下一次宽检查兜底；落地前过决策门。
- 一批任务里串行的契约，计划没写理由 → 决策 4 没被执行，考虑在派发前加提示。
