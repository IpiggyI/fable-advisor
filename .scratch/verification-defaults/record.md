## 3. 成因

问题报告第 1 节的结论：重复检查是结构性问题，由多方叠加造成。没有哪一方能单独解释全部次数，现有证据也排不出哪一方最大。各方的证据与核实状态见问题报告第 5 节。

1. **插件（本仓库）。** 契约第 5 部要求从任务件内联验证命令，所以票据列的全量测试进了每份契约，返工契约又带一遍。合批规则的触发词是「共用昂贵准备」，而全量测试是昂贵的检查，不是准备工作。暂缓一项检查要在契约和任务件里各登记一次。回执只留 2000 字符，主代理只好重跑来看清失败。车道前言没有说明车道内验收与调用方验收的关系，也没有限定车道子代理能跑哪些检查。
2. **cc-usage 的项目记忆。** `spec-must-say-bun-run-test.md`（07-29）要求验证命令「一律写 `bun run test`」，没有区分全量与指定文件；07-31 起的契约大多带全量测试。`cc-usage-app-ts-is-the-parallelism-chokepoint.md` 让 spec 写下「串行执行，一票一提交」，06 至 09 因此逐票往返。会后新写的 `test-run-budget.md` 要求「派活时明确禁止实施者自行跑测试」。这条要求与判定检查冲突，也与椰椰 10-01 声明的检查预算冲突。这三条记忆 2026-10-02 已改，现状见第 7 节。
3. **codex 宿主。** `~/.codex/AGENTS.md` 让 runner 启动的 codex 车道加载 codex-advisor 的编排规则，其中高风险交付要求独立验收。票 13 在车道内跑了 3 轮验收，找到 2 个真实缺陷；主代理的验收又找到车道漏掉的性能回归。两层验收发现的问题不同，覆盖互补。
4. **全局提示词。** 规则 9 要求先确认测试能因正确的原因失败。这类检查代价小、价值高，不改。全局提示词的合批句与插件旧规则用的是同一个触发词。
5. **椰椰的工作流与指令。** 「建票据逐个完成」让 13 张票逐张处理。13:31 椰椰中断前台等待，02 的全量测试被 `SIGTERM` 终止，多了一次全量重跑。15:16 椰椰要求合并测试。16:42 椰椰要求提前结束，批次全量测试因此没有跑，收尾回复已写明这一点。
6. **测试基础设施。** cc-usage 的全量测试单次 150 至 176 秒，仓库没有 DOM 测试环境。rustpad 有 2 个原有失败的浏览器测试，没有登记；每个浏览器脚本都重新启动后端和 Vite。这些因素不制造重复，但放大每次重复的代价。
7. **runner 与宿主机制。** 主会话用前台 `sleep` 等车道，等待期间不能做别的事。
8. **技能与模型判断。** 技能不是成因；`dataviz` 技能带来的 4 次配色计算属于设计工作。主代理把已合并的契约拆成逐票往返，并在第一次派发前自己读了约 255k 的材料。

## 4. 决策

**椰椰的声明与决定**（ADR 0029「决策门核对」第 3、5 项）：

- 检查预算，10-01：「能一起验的就集中一起验（不强求只在最后验一次，防止范围太大验不过来）」。它取代 09-28 的「最多允许一次测试」。
- 10-01 15:36：车道内保留自查，高风险契约保留车道内独立验收；合并后的契约验收一次，提交按授权和回滚边界拆分；先看修订稿。
- 10-01 16:10：`SKILL.md` 词数上限从 2210 上调到 2340；按修订稿实施。
- 修复由主会话在实现姿态下亲自完成，不派 worker。
- 实施完成后发布并部署一版，再写本记录。

**ADR 0029 的决策**（原文见 ADR）：

1. 契约只放本契约改动范围及其调用方的检查，至少带一条判定检查。批次检查不进契约。
2. 全量测试、浏览器或端到端套件、完整构建或打包这类昂贵的宽检查，默认是批次检查：
   - 批次最后一张契约落地后跑一次；只有两种情况提前跑或再跑。
   - 批次大小以失败仍能归因为限。
   - 结果在任务件的 `## Batch checks` 下登记为通过、失败或待跑。有失败或待跑的检查，任务就不算完成。
3. 同一区域的多张票并入一份契约，验收一次；提交只在授权或回滚边界处拆分。
4. 返工契约只带能覆盖失败用例和修复波及范围的最小可运行检查。
5. runner 把每条检查的完整输出写进 `output_log`。日志写不出、或写盘落后超过 16 MiB 时，该字段为 `null`，核验结果不受影响。
6. 车道内评审是自查。调用方复用车道的命令输出，不重跑。车道和它的子代理不跑批次检查。
7. 措辞落在 4 份运行时文件及其中文孪生，共 13 组、26 处替换。
8. `SKILL.md` 词数上限为 2340。
9. 协调件同步：`CONTEXT.md`、`docs/agents/issue-tracker.md`，以及 ADR 0020 与 0022 的状态行。

**没有采纳的方案**（理由见 ADR「未采纳」一节）：

- runner 拒绝带全量命令的 spec；
- 把暂缓做成字段；
- 写盘跟不上时暂停读取命令输出；
- 放大 `output_tail`；
- 在全局提示词里禁止测试；
- 改姿态选择器；
- 派发前固定跑一次基线；
- 禁止车道另起验收；
- 逐票验收与提交；
- 用上下文数字限定并票。

## 8. 遗留项

- ADR 0024 的 P11（编排技能按车道机制分文件）原定在 6.1.0，没有进这一版，时点待椰椰重定。P11 契约的逐句比对基线已经因 ADR 0027、0028 过时（ADR 0029 决策 8）。
- ADR 0027 的端到端行为没有在已安装的插件上跑过：receipt gate 放行在跑的车道，以及 runner 退出后宿主唤醒会话。说明书「已知限制」一节给出了验证步骤。
- ADR 0028 的 TaskStop 宽限只测过一次：SIGTERM 之后约 1 到 2 秒强制结束。
- 历史票据里的 `## Held for batch acceptance` 标题没有迁移，涉及 `.scratch/verification-batching/issues/` 的 01、02，以及 `.scratch/tiers-and-routing-6-0/issues/` 的 01 至 06。新规则只约束之后的任务件。
- `.scratch/verification-batching/spec.md` 的 `Status:` 仍是 `ready-for-agent`，而 ADR 0020 早已落地并随 6.0.0 发布。本次没有改它。
- rustpad 台账 `.fable-advisor/test-ledger.md` 仍引用 `/tmp/count_exec.py`。这个脚本现在是本仓的 `tools/count_rustpad.py`。本次没有改 rustpad。
- 输出日志有上限：写盘落后超过 16 MiB 时，这条检查没有日志（ADR 0029「已知能力上限」）。
- 提示词不是机制：插件规则约束不了项目记忆和宿主的全局规则（ADR 0029「已知能力上限」）。

## 9. 复发时从这里查

### 9.1 先确认加载的版本

1. 在会话记录里找插件路径。技能加载时的 `Base directory` 和 runner 的调用路径都含这一段：

   ```sh
   grep -o 'plugins/cache/fable-advisor/fable-advisor/[0-9.]*' <会话记录>.jsonl | sort | uniq -c
   ```

2. 记录里出现 6.1.0 以外的版本时，先按部署漂移处理，不要分析规则。
3. 在项目目录里启动会话，不要在 `~` 启动（第 6 节）。

### 9.2 统计检查次数

1. runner 的检查看回执：

   ```sh
   python3 .scratch/verification-defaults/tools/receipts.py <仓库路径> <起始时刻 UTC> '<全量命令正则>'
   ```

   cc-usage 的全量命令正则是 `'^bun run test$'`。rustpad 用 `'browser\.mjs|test:browser|^npm (run )?test$|^cargo test'`，因为它的浏览器套件写在 `bash -c` 的循环里。
2. 车道、worker 和主会话的检查，用 `recount_all.py` 作模板：
   - 改文件末尾的会话编号、路径，以及 codex 子代理的时间窗。
   - 改 `recount.py` 的 `kind()`，让它匹配该仓库的命令。
   - rustpad 这类仓库用 `count_rustpad.py` 的 `RULES` 作模板。
3. 沿用同一口径：
   - 一次检查是一条命令段的一次执行，只读命令不计。
   - 上下文取单次模型调用的输入量。一条记录含多次调用（`usage.iterations`）时取最大的一次，不相加。

### 9.3 取证注意事项

- codex 车道经 FastCtx 发出的命令在 `command` 字段里，不在 `cmd` 字段里。只认 `cmd` 会漏计；cc-usage 的自统计就因此少数了 14 次。
- heredoc（用 `<<` 把多行文本交给命令的写法）的正文是写进文件的文本，不是命令。写票时，正文里的验证命令会被切成命令段。`recount.py` 已经去掉 heredoc 正文。
- 循环里的命令只出现一次，却执行多次；契约 JSON 里的命令文本会被误计。这两类要手工数，rustpad 主代理的 34 次就是手工数的。
- 删除工作树会同时删掉其中的回执和输出日志。车道在工作树里运行时，删工作树之前先把 `.fable-advisor/receipts/` 复制出来。
- codex 的 rollout 文件名用本地时间，记录里的时间戳用 UTC。按时间窗找子代理的 rollout 时要换算。
- 回执记的型号是 runner 提交的值。codex 实际用的型号与强度，看 rollout 里 `turn_context` 的 `payload.model` 与 `payload.effort`。

### 9.4 按复盘条件取证

ADR 0029 的复盘条件，以及每条的取证方法：

| 复盘条件 | 怎么查 |
|---|---|
| 实现派发不少于 3 次的会话里，实现回执含全量命令 | 看 `receipts.py` 输出的实现回执数和全量条数。全量条数大于 0 时，看对应契约有没有写提前跑的理由 |
| 批次检查仍为待跑，却被报告为完成 | 读任务件的 `## Batch checks` 和主会话的收尾回复 |
| 批次失败无法归因到某份契约 | 读批次检查的输出或 `output_log`，看失败用例能不能对应到某份契约的 `Files` |
| 已有 `output_log`，主会话仍为看失败而重跑整个列表 | 在 `verification_failed` 回执之后，查主会话的 Bash 命令：有没有重跑同一条检查，有没有读过 `.verification-<n>.log` |
| 车道内评审或验收里出现批次检查 | 在车道记录和子代理记录里找全量命令。codex 要连同子代理的 rollout 一起查，grok 查 `chat_history.jsonl` |
| 并票后的契约仍逐票验收或逐票往返 | 在主会话里找 `do only <票号>` 这类逐票续派，以及逐票的提交 |
| `SKILL.md` 再次逼近上限 | 运行 `wc -w plugin/skills/orchestration/SKILL.md`，上限是 2340 |
| 回执出现 `output_log: null`，诊断为写入落后超过上限 | 看 `receipts.py` 输出的 `output_log` 为空的条数，以及 runner 的 stderr 里有没有 `fell more than` |
