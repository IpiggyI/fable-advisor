# 01: 6.1.0 试用后的统计

Status: needs-info

椰椰会在 cc-usage 里照常做一轮编排开发，用来试用 6.1.0。试用不为评估加任何检查。试用结束后，椰椰在任一会话里说「统计一下」，本票就转为 `ready-for-agent`。统计只读回执和会话记录，不执行任何测试命令。背景见 [前因后果记录](../record.md)。

## 要回答的问题

6.1.0 之后，编排会话还有没有大量重复检查；如果有，来自哪一方。

## 做法

1. 找到试用会话：`~/.claude/projects/-home-hyy-develop-personal-GitHub-cc-usage/` 下 2026-10-02 之后的主会话 `.jsonl`，以及同名目录下的 `subagents/`。先按记录第 9.1 节确认它加载的是 6.1.0；如果不是，只报告版本问题，不往下统计。
2. 对照四个信号：

| 信号 | 怎么看 | 09-28 的基线 |
|---|---|---|
| 契约不带全量测试 | 运行 `python3 .scratch/verification-defaults/tools/receipts.py ~/develop/personal/GitHub/cc-usage <试用开始时刻 UTC> '^bun run test$'`，看全量条数；大于 0 时，看对应契约有没有写提前跑的理由 | 7 张实现回执全部带全量，共 7 条 |
| 全量测试每个批次只跑一次 | 回执里的全量条数，加上车道、worker 和主会话里的全量运行 | 10 次 |
| 检查失败时只重跑失败用例 | 在 `verification_failed` 回执之后，看主会话有没有读 `.verification-<n>.log`，有没有为看清失败而整套重跑 | 票 01 为看清失败多跑了 3 次，其中一次是 152 秒的全量 |
| 并在一起的票只验收一次 | 看主会话里有没有 `do only <票号>` 这类逐票续派，以及逐票的提交 | 06 至 09 逐票往返 |

3. 总次数按问题报告第 2 节的口径数，用 `tools/recount_all.py` 作模板，改会话编号、路径和时间窗。总次数只能与 96 粗略比较，因为两轮的票数和改动量不同。
4. 出现重复时，先按记录第 7 节排除插件之外的来源：三条「复跑」记忆、codex 宿主的车道内验收、全局提示词的合批句。之后再按记录第 9.4 节对照 ADR 0029 的复盘条件。
5. 结果写在本票的 `## Comments` 下，然后把 `Status:` 改为 `resolved`。
